# 05 — Basic interface and chat

Like a car dashboard, the Basic interface shows what the engine reports; it does not invent a gauge when no sensor exists.

The Basic interface is the only available visual interface. The startup picker asks for confirmation even with one option. Claude Code and Codex are the chat assistants.

## Public in-chat controls

In Shell a `/command` without a prefix is the selected assistant's own command (Claude Code or Codex) and does what it does in that assistant's normal terminal. Every command of Shell's own starts with `/f614:`, and no unprefixed alias is left: `/f614:login` (Codex), `/f614:status` (Claude Code), `/f614:refresh`, `/f614:stop`, `/f614:quit`, `/f614:commands`, `/f614:help`, `/f614:yes` and `/f614:no`. An old unprefixed name that no longer exists answers «Unknown command: /x. Use /f614:help.»; every official command of Codex has a route, so «Codex doesn't allow /x from Shell yet» comes out only when the session lacks the method for that command; with Claude Code, `/status` and `/help` are answered by Shell with what it has (see their rows; if Claude Code lists one itself, it is passed on to Claude Code), and any other name is «Unknown command». The names come from each assistant's own list: Codex 0.159.0 (`src/engines/codex/commands.ts`, copied from its `slash_command.rs`) and Claude Code 2.1.274, the version the installed SDK bundles (its commands reference, https://code.claude.com/docs/en/commands).

| Control | Effect |
| --- | --- |
| `/login` (Claude Code), `/f614:login` (Codex) | Connects Shell to the existing native account or offers the official flow. `/login` is Claude Code's own command; Codex has none, so with Codex it is Shell's `/f614:login`. |
| `/logout` | Disconnects only this Shell session; it does not revoke the account. Before disconnecting, Shell asks with a question of its own, not the assistant's permission question: «Disconnect Claude Code from this Shell?» (with Codex, «Disconnect Codex from this Shell?»), with the text that says it only changes this Forge614-Shell session (your native account, Orca, other terminals and saved chats do not change) and which command reconnects, and two options: «No, stay connected» (marked) and «Yes, disconnect». Enter alone or Esc is «No» and neither disconnects nor calls anything; only «Yes, disconnect» disconnects. «Permission requested» and «Allow?» never appear. With Claude Code background tasks running, it first asks whether they are cut (see «Background activity»). |
| `/new` | Starts a new client conversation. With Claude Code, Shell closes Claude Code and opens it again in the background (if the chat had Claude Code open), without resuming the previous conversation and with Engram's memory up to date, so the first message of the new conversation finds it open or waits a moment for it to finish opening. With background tasks running, it first asks whether they are cut (see «Background activity»). |
| `/resume` | Opens a selector of this project's saved conversations, the most recent on top. Each row shows the title, the date, the first message and the folder, only what the assistant reports. Arrow keys move, typing filters (title, first message and folder, ignoring case and accents), Enter resumes the highlighted one and Esc cancels without changing anything. With Claude Code, choosing a conversation makes Shell close Claude Code and open it again in the background (if the chat had Claude Code open) with that conversation and Engram's memory up to date; with background tasks running it asks before closing it, once the conversation is chosen (see «Background activity»). `/resume <number>` (the row's position in that list) and, in Codex, `/resume <id>` still work. With Codex it also works while Codex is answering, as in Codex: the view moves to the chosen conversation and Shell stops following the running turn. The title and first message are the person's: the memory block Shell sends at the start (`<forge614-engram-memory>`) does not count. When resuming (`/resume`) or forking (`/fork`), each old message carries the time of its turn as Codex reports it (`startedAt` for what you wrote, `completedAt` for the answer) and no time when Codex gives none; never the time of now. |
| `/model`, `/effort` | Shows or adjusts options reported by the client. `/effort` is Claude Code's own; with Codex the reasoning effort is chosen inside `/model`, as in Codex, and there is no `/effort` (nor `/thinking`, which neither assistant has). With Codex, `/model` also works while Codex is answering, as in Codex; the new model applies from the next turn and Shell says so. With Claude Code, which stays open for the whole conversation, the model changes at once on that same query (with `/model <model>` Shell says «Model changed: <what you typed>»; picking it in the selector writes no notice and the sidebar already shows the new model), while the reasoning effort has no live change: Shell closes Claude Code and opens it again in the background, with the same conversation and the new effort, and it applies from the next message; with background tasks running, it first asks whether they are cut. With Claude Code, `/model` and `/effort` wait until the turn ends (otherwise they say «Finish or /f614:stop the current turn first.»). |
| `/compact` | Codex: asks Codex's own engine to compact the conversation (`thread/compact/start`) and reports when it is done: as soon as you type `/compact`, the status box says «Compacting context · Making room to continue · 12s», with the time going up, until it finishes: then the box goes back to «Ready» and the chat says «Conversation compacted.» (no progress bar, because Codex reports no real progress; in a narrow box the middle part is dropped and the title and seconds are kept); Engram's memory is sent again with your next message, the same way it is when a thread is opened. Claude Code: passes the command through to Claude Code. A `/command` of Codex's list is answered with «Codex doesn't allow /x from Shell yet» only when the session lacks the method for it, not with «Unknown command». |
| `Shift+Tab` | Works at any moment, also mid-turn or with a permission pending, and does what it does in each assistant. Claude Code: cycles its work modes and takes the change at once on the open query, also between messages, so it is never left «for the next turn». Codex: switches its collaboration mode, Default ↔ Plan, in the order Codex lists them (`collaborationMode/list`), and never touches the permissions (those change with `/permissions`); mid-turn Shell accepts the change and says in one line that it applies from the next turn. The mode row, on the writing box's second-to-last row, keeps showing the permission, adds Codex's «Plan mode» while Plan is on, and its help reads «Shift+Tab: Plan ↔ Default». Shell remembers the collaboration mode and restores it on opening. |
| `↑` / `↓` | The history of what you sent, as in the shells, with Claude Code and with Codex. With the box empty (or the cursor at the start of the first line), `↑` brings the last message or command you sent, `↑` again the one before, `↓` goes back toward the newest and, past the last one, returns what you were writing. Messages and `/` commands go in; answers to questions or selectors (Yes/No, lists) and what comes through `/f614:yes` and `/f614:no` do not. With a menu or a list open, `↑` and `↓` keep moving in the menu. The history is kept per project folder and survives between runs in `~/.forge614/shell/history.jsonl` (permissions 600; one `{"cwd","text","at"}` line per entry): when the chat opens, the last 100 of that folder come back and the file keeps the last 1000 in total. If it cannot be read or written, the history works in memory only and shows no error. `forge614-shell uninstall` removes it together with the rest of `~/.forge614/shell`. |
| `/status` | Each assistant's own. With Codex it shows client-reported state and also lists the folder, the work mode and the conversation, like Codex's own `/status`. Each limit line says when it resets in your local time and language («5-hour limit: 14% used · resets Oct 3, 5:22 PM (last report)»), never as a machine date. Each limit is named by how long its window is, as Codex's own `/status` does: «5-hour limit», «Weekly limit», «Daily limit», «Monthly limit», «Annual limit», or «N-hour limit», «N-day limit» or «N-minute limit» for any other length (each window is recognized with a 5% margin, as Codex does); when Codex reports no length it reads «Usage limit» (the second one «Additional usage limit»), and a limit that is not Codex's own adds its name after the window («Weekly limit · GPT-5.3-Codex-Spark»). It never says Codex's «primary» or «secondary», and the sidebar meters use the same names. The session tokens and the last context read like the sidebar: the totals with each language's thousands separator and the context in short form («Session tokens: input 39,356 · cached 30,208 · output 244» and «Last context: 20.2k / 258.4k»), not raw numbers. With Claude Code, `/status` shows what Claude Code's Status panel shows that Shell really has (see its row below). It ends with one line that says where the memory comes from: «Memory: the assistant delivers it at startup» or «Memory: Shell pastes it» (see «Shell's own memory recall» in the Engram guide). |
| `/status` (Claude Code) | Claude Code's Status panel, with each line only when Shell has the data, and nothing invented: `Version` and `MCP servers` (grouped by state, one group per line and in this order: «Connected: a, b, c», «Connecting: …», «Need sign-in: …», «Failed: …», then «Disabled: …» and «Other: …» for a state without a name of its own; a group with no servers is left out, and a long line continues under its first name, never cutting a name) come from the `init` message of the newest turn, and `Session` from the open conversation, so after `/resume` it already shows; before the first message `Version` and `MCP servers` are left out (and `Session` too, unless a conversation was resumed) and a line says they appear after it, and `/new` clears them again until the first message of the new conversation; `Folder`; `Email`, `Organization` and `Plan` from the account the SDK reports when the catalog loads; `API key` (where the key comes from: `ANTHROPIC_API_KEY`, `apiKeyHelper`, created by `/login`, or none in use) and, when the provider is not Anthropic's own, `Provider`; `Model` and `Permission mode` as the box shows them; `Memory` (where Engram's memory comes from, as in the Engram guide); and `Setting sources` (user, project and local: the files Shell asks Claude Code to load). What Claude Code's panel shows and Shell does not have is not shown: connectivity checks, the IDE and proxy lines, the session name and which `CLAUDE.md` files were found. It also runs while a turn is in progress, but only when Claude Code does not list `/status` itself; if Claude Code lists it, the command is passed on to Claude Code and waits for the turn to end. When Shell answers it, it sends nothing to the model. |
| `/f614:status` | Shell's own, with Claude Code: the session telemetry (model, tokens, context, cost and quotas as Claude Code reports them). Each limit reads like the sidebar, with its plain name, its status in words and its reset in local time («5-hour limit (last report): 31% used | allowed | resets Oct 3, 5:22 PM»; the statuses are «allowed», «allowed, near the limit» and «blocked», and a reset not reported says «reset not reported»); it never shows a provider key such as `five_hour` or a machine date. It used to be `/status` and `/forge614-status`. Codex has no need of it: its own `/status` already shows that. It ends with one line that says where the memory comes from: «Memory: the assistant delivers it at startup» or «Memory: Shell pastes it». |
| `/f614:stop` | Shell's own, in Claude Code and in Codex: cancels the answer in progress. It used to be `/stop`, which now belongs to Codex. With Claude Code it interrupts it without closing it (`interrupt`): the turn ends, the chat says, in red, «You stopped the turn.» (once, even if several messages were queued; if what you stopped was a turn Claude Code started by itself, that line does not appear; the technical name `error_during_execution` is never shown) and the conversation goes on in the same Claude Code. Any other reason a turn is cut (for example, Claude Code dying) still says «Turn stopped: …» with its own message. If Claude Code does not end the turn within 5 seconds, Shell closes it, opens it again in the background with the same conversation (background tasks are left «interrupted») and says «Turn stopped: Claude Code did not answer the stop in 5 seconds…» in your language, if a message of yours was waiting. Stopping also cuts the background tasks Claude Code has running, so with any it first asks «Stopping also cuts N background tasks. Continue?» (with one task: «Stopping also cuts 1 background task. Continue?») with «No» marked; with no tasks it asks nothing. With Codex it asks to interrupt the turn (`turn/interrupt`) and waits for the answer up to 5 seconds; if Codex confirms it, Shell waits up to 5 seconds more for Codex to end the turn; if Codex does not answer in time (Shell then closes that connection, opens it again and resumes the same conversation; only if it cannot reconnect does Shell have to be restarted), answers with an error (for example, that no turn is running) or does not end the turn in time, Shell ends the turn on its side and tells you once, in your language. |
| `/quit`, `/exit` | Each assistant's own «exit» (Claude Code: `/exit`, with `/quit` as its alias; Codex: both): they leave Shell when nothing is running and refuse while a turn, a login or a background task is in progress, saying «Work or authentication is active…» (also with only background tasks) and that `/f614:quit` leaves (it asks before cutting anything). |
| `/f614:quit`, Ctrl+C, Ctrl+D | Shell's own way out, the same with Claude Code and with Codex, and listed in the `/` menu under FORGE614. With nothing running it leaves at once. With Claude Code, if it is quiet but background tasks are running it asks «There are N background tasks; they will be cut. Continue?» (with one task: «There is 1 background task; it will be cut. Continue?») with «No» marked (Enter and Esc cut nothing); if a turn is also running, only the «Quit anyway?…» question is asked, which also cuts the tasks. While a turn, a login or a command runs it asks «Quit anyway? What is running will be stopped.» with «No» marked: Enter and Esc keep everything, and only «Yes» (arrow and Enter, or the letter Y) stops what is running and leaves. With a permission question open it asks to answer that first. It replaces `/quit!` and `/exit!`, which no longer exist. |
| `/f614:refresh` | Requests the quotas that Codex or Claude report again; it sends no chat prompt. It used to be `/refresh`. |
| `/f614:help`, `/f614:commands` | Shell's own: open the menu of commands to choose from. They used to be `/help` and `/commands`; `/help` is now Claude Code's own (see the next row) and Codex has no `/help`. |
| `/help` (Claude Code) | Claude Code's help as Shell can give it: the list of commands with their description — exactly the ones the `/` menu shows under CLAUDE CODE, Claude Code's own first and then the ones Shell carries out with Claude Code's meaning (`/status` and `/help` among them) — one line about Shell's own `/f614:` commands, and the shortcuts Shell respects: Enter (send), Shift+Enter (new line), Shift+Tab (cycle permission modes), Tab (accept the highlighted command in the `/` menu), Esc (close a menu; on a permission question it answers «No») and Ctrl+C or Ctrl+D (leave Shell, asking first while work is in progress; with a permission question open they ask you to answer it first). When the description of a command or a shortcut does not fit the screen's width, the rest goes below its own column (hanging indent); if the width is so narrow that the column does not fit, the description goes on the line below with a fixed two-space indent. Claude Code's other shortcuts (Ctrl+R, Ctrl+O, Ctrl+B, Option+P and so on) are not listed because Shell does not have them. It also runs while a turn is in progress, but only when Claude Code does not list `/help` itself; if Claude Code lists it, the command is passed on to Claude Code and waits for the turn to end. When Shell answers it, it sends nothing to the model. |
| `/f614:yes`, `/f614:no` | Shell's own: answer a pending permission by typing (the selector with «Yes» marked is the normal way). They used to be `/yes` and `/no`. |
| `$name` | Codex: the `$` autocomplete lists Codex's own catalog of skills (reusable instructions) from `skills/list`, plugins included and switched-off ones left out. Each recognized `$name` in a message is sent to Codex as a real skill (`{ type: "skill", name, path }`) next to the message text, which stays as written; a `$word` that is no skill stays text only. Choosing a skill from the list with Enter or Tab only writes `$name ` in the box, as Codex does, and you go on writing: the next Enter sends the message. The list is titled «CODEX SKILLS» and counts «Skills · 1–5 of 56» (in Spanish «HABILIDADES DE CODEX» and «Habilidades · 1–5 de 56»); the `/` menu still sends the command with Enter. |

With Codex, the `/` menu (and `/f614:commands`) lists Codex's commands with Codex's own description, in Codex's order, and only the ones Codex shows on macOS; Shell's own (`/f614:login`, `/f614:refresh`, `/f614:commands`, `/f614:stop`, `/f614:quit`) sit apart under FORGE614, the only group whose commands carry a prefix. When the sidebar is not on screen (the person hid it, or the terminal is under 100 columns), the status bar also carries the model, the reasoning and the context, as explained in «Sidebar metrics». The history shows the conversation, with each tool call indented under the assistant message it belongs to. “Not reported” means exactly that the client did not provide the value. The interface has no Gemini or Antigravity screens or commands.

Under the request there are only two rows with words, «Yes» and «No» (in Spanish «Sí» and «No»), with «Yes» first and marked so Enter alone approves; the down arrow (or the `N` key) chooses «No», the `Y` key chooses «Yes», and Esc is «No». A single footer says how to move and that `/f614:stop` cancels the turn. Typed `/f614:yes` and `/f614:no` still answer the pending question, but the screen no longer mentions them.

## Visible startup and welcome

Like waiting for an elevator while its arrow is moving, startup makes it clear that Shell is still working while it asks which engines are available.

In an interactive terminal, Shell displays the `Detecting installed AI engines…` spinner before opening the picker. Detection uses an asynchronous child process (`execFile`), rather than a synchronous wait that would freeze the process, so the animation can continue updating. On non-TTY output, it prints the same message once without animation. When the query finishes, the indicator is cleared and the normal flow continues.

The welcome frame renders `FORGE614` in bold and shows the Shell version as `v<version>` on the right when the terminal is wide enough. This identifies the application; it does not claim a Claude Code or Codex version.

Before the first person message in a Claude Code or Codex chat, Shell also draws a centered `FORGE614` sign in the visible chat area: its top padding is half (rounded down) of the rows left after the sign, and notices written before that first message appear below it. The columns are those of the chat area, not of the terminal: with the sidebar visible (from 100 terminal columns) the chat is the terminal width minus the sidebar's width (36 columns unless changed) and minus the grip's 2 columns (38 with the usual width); with no sidebar it is the whole terminal. `FORGE` is muted and `614` is bold foreground; the hollow cells are ordinary spaces, with no shadow background. With 82 chat columns or more it uses a five-row double-size sign; from 43 to 81 it is three rows, with `FORGE` and `614` side by side; from 26 to 42 it stacks `FORGE`, one blank row, then `614`; from 18 to 25 it uses `F614`. Below 18 chat columns or below 12 terminal rows it is absent, and then it leaves no blank padding rows either: notices sit on the first row of the chat. The sign disappears as soon as the person sends something to the assistant: a typed message; with Claude Code, a native command sent as a turn (such as `/init`); with Codex, `/init`, `/plan <text>` (if Plan mode exists: if not, only the notice is written and the sign stays), `/side <question>` and `/btw <question>` (only if the side conversation opens; with no question, or if it cannot open, the sign stays) and `/review` (as soon as something to review is chosen, or given with `/review <text>`; if its picker is closed without choosing anything, the sign stays). Shell's own `/f614:…` commands, Codex's `/compact` (Claude Code's is a native command and does remove it, like `/init`) and a rejected message do not remove it. `/new` (and anything else that clears the chat view, such as `/resume`) also removes it, even before a first message, and it does not come back in that session. The exception is a view set aside only for a moment: leaving a Codex side conversation or a subagent view returns the main view as it was, so if there was no first message yet the sign is still there. The startup frame is unchanged.

`forge614-shell --help` and `-h` use the normal sign sizes only, never the double-size one. On a terminal they use color and the available width, up to 81 columns (without the height rule); below 18 columns, or with an unknown width, they print no sign or blank row. When piped, they always use the three uncolored side-by-side rows, whatever the width, so scripts receive stable plain text.

While a Shell screen (Claude Code's or Codex's) occupies the terminal, no Node process warning is written raw on top of it: Node prints those warnings on the error output and the text used to land on the screen Shell draws. Shell takes them when the screen opens (it removes Node's own printer in the meantime) and, when the screen closes, gives the printer back and leaves the process's warning listeners as they were. The `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` warning («canUseTool will not be invoked», which the Claude Code SDK raises when a query opens in «Bypass Permissions») is ignored without showing anything: it is expected, because Shell passes `canUseTool` on purpose on every query so it can leave «Bypass Permissions» live. Any other warning shows as a normal Shell notice inside the chat, on a single row with muted text (cut with «…» if it does not fit) and the prefix «Node warning: <message>», without the «(node:<pid>)».

## Look: borderless blocks, neutral grays, and colors that adapt

Like a dark room where every table is a little lighter than the floor, the screen draws no boxes of lines: each zone (sidebar, writing box, cards, code blocks, the chosen option) is a block of background a little lighter than the general background, and separation comes from contrast and space. Secondary text is a muted gray and states are told apart by the color and icon of their text. The screen is always dark: while it is in the alternate screen, Shell puts the general background and the base text color behind everything it writes (`workspaceTerminal`), including the startup screens, and resets them on leaving.

Every color lives in one file, `src/ui/basic/theme.ts`. The grays are nearly neutral (no marked blue tint: the blue channel runs 1 to 9 points above the other two); the 256-color index is what a terminal without true color uses:

| Name | RGB | 256-color index | Where it is used |
|---|---|---|---|
| `background` | 10;10;11 | 232 | the screen's general background |
| `surface` | 24;24;27 | 234 | sidebar, writing box, cards, code blocks |
| `elevated` | 39;39;42 | 235 | the cursor option in the writing box's menus, the «jump to latest» button |
| `foreground` | 228;228;231 | 254 | text |
| `muted` | 161;161;170 | 248 | secondary text |
| `faint` | 63;63;70 | 238 | the empty part of the usage bars and the ring, the Markdown `---` rule, the grip's dots at rest |
| `accent` | 70;222;224 | 80 | accent (the cursor's «▎» bar, chat headings, the sidebar's section titles, the grip's arrows and dots while hovered or dragged, the buttons under the pointer, the chat's links and paths) |
| `accentBright` | 150;245;247 | 123 | the chat's link or path with the pointer over it (together with bold and underline) |

Status (`success`, `warning`, `danger`), diff (`added`, `removed`, `addedBackground`, `removedBackground`) and mode colors (`purple`, `planning`, `magenta`) keep their value.

**Colors that adapt.** Every time it paints, `theme.ts` asks pi-tui's `getCapabilities().trueColor`, which decides from the terminal: a recognized one (kitty, Ghostty, WezTerm, Warp, iTerm2, Windows Terminal, Alacritty, VS Code, Zed, JetBrains, the Windows console) has true color; inside tmux or screen, and in any unrecognized terminal, true color only if `COLORTERM` is `truecolor` or `24bit`; `PI_TRUE_COLOR` (`1` or `0`) overrides all of it. With true color it emits `38;2` / `48;2` (RGB); without it, the nearest index of the 256-color palette (the 6×6×6 cube and the 24-step gray ramp) with `38;5` / `48;5`, also for the alternate screen's general background and base text. The person is told nothing. There is a single conversion function (`nearestAnsi256`), tested with exact values. With 256 colors, the red and the green background of a diff's rows both land on gray 235 (the cube has no greens or reds that dark); their `+` / `-` signs and the text color still tell them apart.

**What changed in form.**

- The writing box is a block of the `surface` background edge to edge, with two columns of margin on the general background and six rows: a blank one, a padding row, the editor, a padding row, the status-and-mode row and a closing padding row. The status no longer has a row of its own above the editor: it sits at the left of the mode row (see «Live status, model, and reasoning»). In the writing box's menus (`/` commands, selectors), the cursor's option is a row of the `elevated` background with an accent «▎» bar instead of «›»; the other rows have no background. The right margin of the rows with a block is painted on purpose with the general background (`palette.background`) when there is a margin (from 14 columns of chat width; narrower, the writing box has no margin), because the block's painter ends with «reset background» and those columns, with no color of their own, would show the terminal's own tone as a strip next to the block; the left margin draws nothing and the block does not change.
- The header keeps its three rows, without the rule below; it starts in the same column as the writing box's block (two columns in from the chat's left edge, from 14 columns of chat width; narrower, no margin) and says only «FORGE614 / SHELL»: the folder no longer appears at its right, it is in the status bar. While the person has hidden the sidebar, the same row carries the «‹ show sidebar» button at the chat's right edge, with two columns of margin (muted gray, cyan under the pointer), which shows the sidebar again at its last width; on a terminal under 100 columns it does not appear.
- The sidebar is a column of the `surface` background from the top down to the last row of the terminal, with no «│» and two columns of padding on each side; the two columns between the chat and it keep the general background, which is where the contrast comes from (the grip lives there, drawing only dots and arrows with no background of its own; see «Sidebar metrics»). On a terminal narrower than 100 columns it is not shown, and no button to show it is offered. The status bar and the blank row that separates it from the writing box sit only under the chat column, not under the sidebar; the bar's text keeps its side columns (it starts two columns in from the chat's left edge, like the writing box; the writing box has that margin from 14 chat columns, and narrower it has none, while the bar keeps its two columns) and, only when it fits, the `v<version>` ends in the same column where the writing box's gray block ends; its own lower blank row remains. Without the sidebar the status bar takes the whole width. Section titles (`// SESSION`, `// CONTEXT`, `// PLAN USAGE`, `// BACKGROUND ACTIVITY`) are the accent color (cyan) in bold, in uppercase, with no rule under them and an empty row before their content; the space between sections stays. Clicking background-activity rows still works.
- The «jump to latest» button is a single row of the `elevated` background, with no box.
- A tool's full card (a diff or a permission) is a `surface` block with one column of padding on each side and a padding row above and below, set in two columns from the chat's edges, with no «│».
- Code blocks in the chat no longer have the «───» line: the code sits on `surface`, the opening row keeps only the language (if any) in secondary gray and the closing row is empty. pi-tui's Markdown component only hands the theme the text of those two rows, so they cannot be filled edge to edge or given a background; the block's background sits behind each code row, as far as its text reaches.
- At startup, the rule under «FORGE614 / SHELL» and the one separating groups from actions on the group screen are now a blank row: the height is the same.
- The usage bars and the ring keep `█`, `░` and braille, with the empty part in `faint`.

## Transcript: activity, changes, and errors

Like a flight log, the history distinguishes routine events from moments that need inspection or a decision.

Routine tool calls—searches, reads, Bash, MCP/Engram, and similar events—render as a bullet with no controls of its own (only the paths in it that exist are clickable, see «Links and file paths with a click») and, when available, one detail-preview line underneath. They have no border, background, or expand control: the summarized activity is all that is presented. Permission requests retain a full card (a borderless `surface` block) because the person needs to read the context before deciding.

When Claude Code reports an `Edit` or `Write`, Shell shows a line-level diff instead of the tool's raw JSON: removed lines are red, added lines are green, context lines are muted, and a gutter shows line numbers. To keep the chat responsive, ordinary changes use a longest-common-subsequence comparison, oversized files fall back to a coarse view, and the display limits the diff to 60 rows before noting that more remain.

Claude Code and Codex both use an independent transcript view. Once you scroll away from the newest message, the floating `↓ New messages · jump to latest` button (a single row of elevated background, no box) appears beneath the header, centered over the chat column (not the whole terminal: it follows the sidebar's width and whether it is hidden); clicking it returns to the end. It hides automatically when the view is following the end again.

Errors such as a stopped turn, invalid command, invalid pending-permission response, or connection failure are inserted in red. `ChatText` accepts a base color so Markdown formatting preserves that visual signal instead of blending an error into an ordinary reply.

## Links and file paths with a click

It works the same with Claude Code and with Codex. A simple left click — press and release on the same spot (the same character cell) of a link, with no dragging — opens what is drawn underlined or in cyan in the chat; pressing and releasing somewhere else (even inside the same link), dragging in between, or a double or triple click is a text selection and opens nothing.

**What becomes clickable.**
- *Web links* in the chat's text (the assistants' messages, also yours, Shell's notices and errors): Markdown `[text](address)` ones and an address written on its own (the one the screen's Markdown recognizes). They are drawn in cyan and underlined. Only `http:` and `https:` addresses are opened, with a port too (for example `http://localhost:3000`) and with no user or password inside; any other scheme (`javascript:`, `file:`, `ftp:`, `mailto:`…), an address with a user or password, and a link an assistant writes imitating Shell's own are drawn but open nothing. They open in the browser through the system's own launcher (`/usr/bin/open` on macOS, `xdg-open` on Linux, `rundll32.exe` on Windows), with the address as one separate argument and never through a shell.
- *File paths* in the chat's text (also inside `inline code`) and in tool cards (the title, the first line of the detail and the body of full cards, such as a permission): absolute, with `~/`, with `./` or `../`, or relative to the session's folder (also a bare name with an extension, such as `package.json`). It is a link only if it **exists on disk at the moment the message is drawn** (and it is checked again on click); a path that does not exist stays as text. It may end with `:line` or `:line:column`: the link shows it, but the file is opened without the suffix. Paths do not become links inside code blocks, in the lines of a diff, in headings (`#`) or in quotes (`>`). Paths containing spaces are not recognized (the link would end at the first space), and Windows paths only if they use `/` (`C:\folder\a.ts` is not a link; `~/` needs the `HOME` variable to exist). They are drawn in cyan, without underline.
- *Markdown links to a local path*, such as `[app](./src/app.ts)` or `[log](/tmp/x.log)`: a destination with no scheme — absolute, with `~/`, with `./` or `../`, or relative to the session's folder, with or without `:line` or `:line:column` — is treated as a path of the text. It is a link only if the path exists when it is drawn, it opens with the same opener and the same safety rule (what is shown in Finder is still shown in Finder) and it lights the same way with the pointer over it. If it does not exist, it is drawn like any other Markdown link (with the address as written, as the library does) and opens nothing. `file:` and any other scheme are still not opened.

**How a path opens.** On macOS, with `/usr/bin/open <path>`: the file opens with the app the Mac has for it and a normal folder opens in Finder. On Linux, with `xdg-open`. On Windows Shell never opens a file: a folder opens in Explorer (except a package folder from the list below, which is shown selected) and a file is shown selected in it (`explorer.exe /select,<path>`, one argument). Always with no shell; on macOS and Linux the path is one separate argument.

**What is shown in Finder instead of opened, and why.** Shell itself runs nothing because of a click: what the system could run or install, by a fixed list, is shown instead of opened (everything else opens with the app the system has for it). So, instead of opening, it shows in Finder (`/usr/bin/open -R <path>`; on Linux the folder that holds it is opened) an app or package (`.app`, `.bundle`, `.framework`, `.plugin`, `.kext`, `.pkg`, `.mpkg`, `.workflow`, `.xpc`, `.appex`, `.prefpane`, `.saver`, `.component`, `.action`, `.dext` and `.systemextension` folders), a file with the execute permission and a file with the extension `.command`, `.tool`, `.terminal`, `.sh`, `.zsh`, `.bash`, `.pkg`, `.mpkg`, `.dmg`, `.workflow`, `.scpt` or `.applescript` (case does not matter). A symbolic link is judged both by its own name and by what it points to: one named `notes.txt` that leads to an app is shown, not opened, and so is one named `x.sh` that leads to a text file.

**The terminal's hyperlinks.** Web links reach the terminal as OSC 8 hyperlinks. The screen library (pi-tui) leaves them off in macOS Terminal and in Orca, which it does not recognize; Shell turns them on in those two (`TERM_PROGRAM` equal to `Apple_Terminal` or `Orca`) as well as wherever the library already detects them. Under tmux hyperlinks work only if tmux declares that it forwards them (`client_termfeatures` includes `hyperlinks`); under screen there are none, unless `PI_HYPERLINKS` is set. In both, Shell does not turn them on even when the outer terminal is macOS Terminal or Orca. If `PI_HYPERLINKS` is `1` or `0`, its value rules (`1` turns them on, `0` off); any other value is ignored and Shell does not turn them on by itself either. Where hyperlinks are off there are no links (Markdown ones come out as «text (address)»). The click is handled by Shell's screen, not by the terminal.

**With the pointer over it.** The whole link — all of its columns, also the following rows if it wraps (except inside a quote `>`, where each row lights separately) — is drawn brighter, in bold and underlined; when the pointer leaves it goes back to cyan. There are no borders, boxes or colored backgrounds. Also, while the pointer is over a link, Shell asks the terminal for the hand pointer (OSC 22, `pointer`) and gives it back (`default`) when it leaves the link, when something else is pressed and when the screen closes; it does not take it from the sidebar's grip if the grip holds it. The mouse arrow changes only in terminals that understand that request; macOS Terminal and Orca do not, and there the signal is the color.

**If opening fails.** If the system's launcher reports an error or the path no longer exists, the chat shows one amber line with the text «Could not open» followed by the path or the address (`chat.linkOpenFailed` in `src/i18n/en.ts`), and nothing else breaks.

## Live status, model, and reasoning

Like the signal light on an operations console, the composer tells you whether writing can proceed, the engine is busy, or a human decision is needed.

The status lives on the mode row, at the left of the mode text and separated from it by a faint « · »: «<status> · <mode>», with the shortcuts on the right. When it does not fit, the shortcuts go first, then the middle part of the status (never the time) and last the row is clipped. The status is told apart only by the color of its text and its icon, with no backgrounds of its own, boxes or lines: «✓ Ready» is green; `Working` (and «Compacting…» or the recap) carries the braille spinner in amber, its first part under a band of light that sweeps across it and the rest («· reading hola.sh · 12s») in gray; «Waiting for your answer» is red with a «●» that pulses; the other states («Checking account», «Connect with /login») carry a fixed «●» in the color they already had. «Waiting for your answer» shows for as long as Shell waits for you — a confirmation, a command's selector, a question or a permission request — even while the assistant is still working, and the box goes back to `Working` (or `Ready`) when you answer.

Three animations, all computed by mixing the palette's colors (so they adapt to 256 colors): the band of light moves 7.5 letters a second from 3 letters before the start of the word to 3 after its end and starts again, and each letter blends between a dim amber and a bright one by its distance to the band; the «●» of «Waiting for your answer» goes back and forth between the red and the red mixed halfway toward the surface gray, one turn every 1.6 s; and when the status goes from working to «Ready», «✓ Ready» starts mixed 60 % toward white and returns to green in 0.6 s (a «Ready» that does not follow work, like the one at opening, does not flash). While anything is animated (working, waiting or the flash) the screen repaints every 100 ms; when nothing is, no timer is left running. During an active turn, Claude Code and Codex also refresh the status every half second and show elapsed time, for example `Working · 12s`; during `/compact` in Codex the box says «Compacting context · …» instead. When a tool or command is running, the status also says what it is doing, for example `Working · Waiting for the PR #3 checks · 8m 23s` (the tool's description in Claude Code; the command, on a single line, in Codex); when none is running, only the time. Every time counter in Shell (this indicator, each tool and the sidebar) uses the same format: `45s`, `1m 27s`, `8m 23s`, `1h 02m`. A long command takes a single line in the chat that updates in place and freezes with its result when it ends. The counter stops when the turn finishes or is cancelled.

The `/model` and `/effort` menus are deliberate choices: they number options, align the primary column, and mark the active value with `✓` even while the cursor is on another option. This keeps the focused option distinct from the setting that will actually be used.

For Claude Code, the sidebar first tries to show the catalog's friendly name—for example, `Opus (1M context)`—rather than a technical identifier. If the selected value or telemetry has no exact catalog match, it turns the identifier into a readable fallback without inventing a product name.

Shell remembers selected model and reasoning independently for `claude` and `codex` in `~/.forge614/shell/preferences.json` (or under `FORGE614_HOME` when that is set). It also remembers the last assistant used (the startup picker marks it as «last used» and highlights it, so Enter accepts it) and, for each assistant, the last work mode, whichever it was (full access included), which it restores on opening without asking, and the sidebar's width and whether it is hidden (see «Sidebar metrics»); a saved mode the assistant no longer has leaves its default mode, with no error. This is Shell-owned preference data; it does not modify the native CLI configuration. Reading and writing are best-effort conveniences: a missing or malformed file, a failed write, or a model no longer offered lets the session continue with available values.

In the sidebar, no explicit reasoning level is labeled `Default (auto)`. Claude Code's reasoning picker shows `Default (recommended)` and explains `Claude Code decides — shown in the sidebar after you send a message`: Claude does not report the concrete level it will resolve in advance, so Shell states that fact rather than guessing.

## Sidebar metrics

Like keeping consumption instruments beside the fuel gauge, the sidebar groups usage information together. Since 1.13.0 it no longer has the `RESOURCES` section (Shell's RAM and the engine's RAM): it was removed whole, with its Spanish and English text.

The latest message's tokens and the estimated amount sit under `PLAN USAGE`. They are written in plain words over short rows, never cut off: `This message` / `read 2,996 tokens` / `wrote 700`, then `If you paid per use` / `≈ $0.67` / `your plan doesn't bill it`. The amount is a reference estimate, not a charge billed by Shell or by your plan; under one cent it reads `under $0.01` instead of zero.

Until the context has a figure, the `CONTEXT` section says when it will appear, in a short text that fits the sidebar's width: `after 1st message` while the conversation has no id (a new Claude Code one), `after the next message` once it has one and nothing has been measured yet (a resumed one, or a Codex one, which opens when the chat starts). Once there is a figure, the percentage in the circle is written as text (not blocks) with its «%» («8%») and in the same alert color as the circle, on the circle's middle row and centered in it (a width of two or four cells, «8%» or «100%», can only sit half a cell to the left of the exact center); the percentage is also written beside it. The circle is always 13 cells wide and 7 rows tall, so a narrow sidebar is not broken.

The sidebar also takes over the left button's press, drag, and release, like the composer, so selecting text in the chat with the mouse no longer highlights the sidebar. What you select stays on its text even if you scroll the screen with the wheel (except while a bottom-bar panel is open), and when you let go of the button it is copied whole, including the part that is no longer in view, to the system clipboard (macOS Terminal included) and the notice says «Copied». It is copied with the system's own program (`pbcopy` on macOS, `wl-copy` or `xclip` on Linux, `clip` on Windows); if there is none or they fail, Shell sends the OSC 52 sequence to the terminal and still says «Copied», even if the terminal does not understand it; «Copy failed» shows only if even that could not be written. Cmd+C is not needed: the selection is copied by itself when the button is released (the terminal's Cmd+C copies what the terminal itself has selected, not Shell's selection). If you let go of the button over the sidebar, the header, the writing box or the bottom bar, the selection ends and is copied all the same, up to where it got in the chat. And if the chat's width changes (the terminal is resized or the sidebar changes its width), the selection is removed, because the text is laid out again and would no longer match.

**Dragging, folding and remembering the width.** Between the chat and the sidebar there is a two-column grip. At rest it draws only a faint `⋮` in its second column, on the five rows around the terminal's middle row, with no background of another color (nothing that looks like a scroll bar). With the pointer over it, or while it is dragged, it draws `◂▸` (both columns) on the middle row and `⋮` on the other four, all in cyan, and Shell asks the terminal for the resize pointer (OSC 22, `ew-resize`); it gives it back (`default`) when the pointer leaves the grip, on release and when the screen closes (a terminal that does not understand OSC 22 ignores it). The mouse arrow only changes in terminals that understand that request; macOS Terminal and Orca do not, and there the signal is the grip's dots turning cyan with ◂▸. No text is shown while dragging (except the folding notice, below). Pressing on the grip captures the drag and starts no text selection. The sidebar's width follows the pointer and the column that was taken on press stays under it, with no jump when the drag starts; it runs from 28 to 70 columns and the chat never has fewer than 60 (on a 100-column terminal the sidebar reaches 38 at most; on 120, 58). If the width falls under 28 but not under 24, it stays at 28.

If dragging takes the width below 24 columns, the sidebar is drawn 24 wide and, instead of its content, says «release to hide it» in amber (if it does not fit on one row, it continues on the next); releasing there hides the sidebar, and the width it had stays saved. There are also two buttons, both muted gray and cyan under the pointer: «hide ›», on the sidebar's first row (the empty one at the top), right-aligned with two columns of margin, and «‹ show sidebar», on the header row while the sidebar is hidden (see above). A click on the first hides it; a click on the second shows it at its last width. On a terminal under 100 columns the sidebar hides itself, as before, and the button is not shown; a saved width larger than what fits is drawn narrower (the chat keeps its 60 columns) without being forgotten.

The width and whether the sidebar is hidden are saved in `~/.forge614/shell/preferences.json` (or under `FORGE614_HOME` when that is set) as the root-level fields `sidebarWidth` and `sidebarHidden`, when the mouse is released or a button is clicked: never while the mouse is moving, and pressing and releasing the grip without moving it saves nothing. A `sidebarWidth` that is not a number, or that once rounded to whole columns is not between 28 and 70, is ignored and counts as 36; a `sidebarHidden` that is not `true` counts as «on screen». What is saved is the width the pointer asked for (from 28 to 70), even if the terminal only has room to draw less. It works the same with Claude Code and with Codex.

While the sidebar is not on screen (the person hid it, or the terminal is under 100 columns), the status bar's row carries, right after «F614 ▴» and before the folder, the model (normal text), the reasoning (amber, as in the sidebar; with no explicit level it reads «Default (auto)», as in the sidebar) and «context N%» (normal text), separated with « · » like the rest; only what is known and only with a connected account, and if it does not fit it is cut with «…» like the rest of the row. With the sidebar on screen they are not repeated.

**The bottom bar and its two panels.** The status bar starts with «F614 ▴» and, at the right, right before the version `v<version>` and three spaces from it, shows «⇌ N MCP ▴», where N is the number of MCP servers that are connected (the ones starting, failed, cancelled, disabled or needing a sign-in are not counted). Both are cyan and are touched with a left click on their text; the arrow says whether their panel is closed (▴) or open (▾). There is no hover effect: moving the pointer over the bar changes nothing, only the click does, and only on the indicator's text. «F614 ▴» opens the «Forge614» panel and «⇌ N MCP ▴» opens the «MCP servers» panel. A click on the same indicator closes its panel, a click on the other one switches panels, and a left click anywhere else (the click only closes the panel and does not reach what is under it) or Esc closes it; moving the pointer, the wheel and the other buttons do not (with a panel open, Esc only closes the panel: it does not reach the writing box or anything that stops the assistant's work, and typing in the box keeps working). The panels are a block of the `surface` background with no border or shadow, with an empty row above and below and two columns of margin, right above the bar; the Forge614 one aligns its left edge with «F614» and the MCP one its right edge with the end of «⇌ N MCP ▴»; they are never wider than the chat, and if all their rows do not fit, the ones that fit are shown and a last «+N more». If its indicator stops being drawn (no room, or the MCP data is gone), the panel closes with it. While Shell knows nothing about the MCP servers the «⇌ N MCP ▴» indicator is not drawn: with Claude Code, until Claude Code answers (it appears a few seconds after the chat opens, with no message sent, because the query Claude Code keeps open for the whole conversation is the one asked, and it does not disappear with `/new`) or if neither that answer nor the `init` message carries the list; with Codex, Shell opens the conversation as soon as the chat is ready, like Codex's own window, and the indicator appears a second or two later with no message sent (it is not drawn until the list arrives, nor if Codex cannot give it); and with either assistant, while the account is not connected. When the line does not fit, the end of the left part (folder, branch and changes, the last things on the line) is cut with «…» first, leaving room for «⇌ N MCP ▴» and the version, so a folder with a long path no longer hides them; only if that left part would be left with fewer than 20 visible columns is the version given up and, if it still does not fit, «⇌ N MCP ▴»; «F614 ▴» stays as long as it fits, and the rest of the line is cut with «…» as always.

The «MCP servers · <total>» panel has one row per server: a «●», the name and the word of its state, the «●» and the word in the state's color: «connected» (green), «starting» (amber), «needs sign-in» (amber), «failed» (red), «cancelled» (gray) and «disabled» (gray); a server with no state (Codex reports none, or the assistant used a word Shell does not know) has only the gray «●», with no word, and is not counted in N either. The `forge614-engram` server also carries «Forge614 · Engram» in cyan. The data is not asked for again after each message: with Claude Code, when the chat opens Shell opens Claude Code in the background and keeps it open for the whole conversation (a single query for the catalog, the messages and this; it opens it again only if you change the effort, it does not answer a stop, it dies, or with `/new` and `/resume`; opening it sends no message to the model and spends nothing from the plan); over that same query it asks for the MCP servers and, while any is still starting, asks again every 2 seconds, 30 at most each time; with no server starting it does not ask again (the opening question is asked once), there is no running clock (if the query fails or does not answer, the indicator is not drawn and not retried; it appears with the first message's `init`). Each message's `init` also counts, but it never lowers to «starting» a server whose state is already known (the `init` is written while the servers are still connecting) and, if it lists any as starting, Shell asks again the same way (every 2 seconds, 30 at most); `/new` does not clear the list, because it is Claude Code's configuration and not the conversation's (the new query `/new` opens asks for it again); with Codex it comes from a single query (`mcpServerStatus/list`) made right after the conversation opens, with its id (without it if it could not be opened), and after that only from Codex's notices (`mcpServer/startupStatus/updated`) that belong to this conversation or carry no conversation (a notice of another conversation is ignored; one of a server that was not on the list adds it; a notice that arrives before the list rules over it for that server). `/mcp` stays as it was. The «Forge614» panel has three rows with the name in gray and the version in normal text: «Shell» (the version the bar already shows), «Engines» and «Engram»; the Engines and Engram versions are read only once, in the background, when Shell opens (`--version` of each binary, with a 3-second limit), and if the binary does not exist the row says «not installed» in gray (if it exists but did not answer, the row has no version). On Engram's row it says «memory in use» (green) if Engram's startup context of this session arrived, «not in use» (gray) if Engram is installed but it did not arrive, and nothing while it is not known (with Claude Code it is known as soon as Shell opens it in the background, when the chat opens and with no message sent; with Codex, as soon as Shell opens the conversation, shortly after the chat is ready and with no message sent, or when the first one is sent if that opening could not be done).

Compact counts use `1M`, not `1000k`, and retain one decimal only when it adds information: `1.5k`, `43k`, `1M`, and `1.5M`. The context ring and filled portions of usage bars share an alert scale: normal below 85%, amber from 85%, and red from 100%. Color therefore conveys proximity to the limit, rather than merely a visual preference. The percentage in the middle of the context ring is text (not blocks) with its «%» («8%») and in the same alert color as the ring; the ring is 13 cells wide and 7 rows tall.

## Background activity

When the active engine reports background work (Claude Code subagents, backgrounded processes), the sidebar shows a single line per activity, with its title, its state (running, done, failed) and elapsed time (when the title is long, the title is cut, not the state or the time); clicking it expands to show the result if the engine delivered it. The status bar adds a counter with an animated dot while activity is running (between messages the dot and the times only update when an event arrives or every 15 seconds; they do not animate on their own; with the sidebar on screen this is what remains there besides folder, branch and Git state). If the engine does not report this distinctly, the sidebar says so explicitly instead of silently showing an empty list — see `docs/superpowers/specs/2026-09-22-background-activity-indicator-design.md`. With Claude Code, a task's state can also be «interrupted»: in the sidebar a task only becomes «interrupted» when Claude Code is closed or dies; a task Claude Code reports as stopped shows «stopped» on its card and «failed» in the sidebar. The tasks live inside the Claude Code that Shell keeps open for the whole conversation, so they go on between messages: the sidebar and the counter are not emptied when a turn ends, and while the assistant is not speaking and some task is still running the status box says, in amber and with «●», «Ready · N in the background» instead of the green «✓ Ready». When a top-level task finishes, Claude Code says so and Shell draws a card in the chat with the task's title, its state (finished, failed, stopped or interrupted) and the summary Claude Code gives; tasks a subagent starts on its own and housekeeping (ambient) ones draw no card. A helper's inner steps (the tools it uses inside and their results) are not seen in the main chat, as in Claude Code: of the helper you see the «Agent» line of the main assistant, the card of its task when it ends and the «Background activity» panel; the permissions a helper asks for are asked the same way. After that Claude Code usually starts a turn by itself, with no message from you, to deal with that notice: Shell draws its answer like any other and the box says «Working» until that turn ends. What Claude Code says on its own about its tasks (for example, when resuming: «N background agents didn't finish…», as Claude Code gives it) is drawn as a «Notice from Claude Code» card, not as a message of yours. The tasks live in the process: if Claude Code is closed or dies, the ones that were running are marked «interrupted» (not «done», and not deleted) until your next message, which forgets the ones already over. That is why leaving with Claude Code quiet (`/f614:quit`, Ctrl+C, Ctrl+D), `/new`, `/resume`, `/logout` and changing the effort with tasks running ask first «There are N background tasks; they will be cut. Continue?», with «No» marked (Enter or Esc cut nothing), and `/f614:stop` asks «Stopping also cuts N background tasks. Continue?» because Claude Code kills them together with the turn; with no tasks running nothing is asked.
