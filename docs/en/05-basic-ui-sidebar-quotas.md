# 05 — Basic interface and chat

Like a car dashboard, the Basic interface shows what the engine reports; it does not invent a gauge when no sensor exists.

The Basic interface is the only available visual interface. The startup picker asks for confirmation even with one option. Claude Code and Codex are the chat assistants.

## Public in-chat controls

In Shell a `/command` without a prefix is the selected assistant's own command (Claude Code or Codex) and does what it does in that assistant's normal terminal. Every command of Shell's own starts with `/f614:`, and no unprefixed alias is left: `/f614:login` (Codex), `/f614:status` (Claude Code), `/f614:refresh`, `/f614:stop`, `/f614:quit`, `/f614:commands`, `/f614:help`, `/f614:yes` and `/f614:no`. An old unprefixed name that no longer exists answers «Unknown command: /x. Use /f614:help.»; every official command of Codex has a route, so «Codex doesn't allow /x from Shell yet» comes out only when the session lacks the method for that command; with Claude Code, `/status` and `/help` are answered by Shell with what it has (see their rows; if Claude Code lists one itself, it is passed on to Claude Code), and any other name is «Unknown command». The names come from each assistant's own list: Codex 0.159.0 (`src/engines/codex/commands.ts`, copied from its `slash_command.rs`) and Claude Code 2.1.274, the version the installed SDK bundles (its commands reference, https://code.claude.com/docs/en/commands).

## Engram memory activity

Like seeing the archive-room light turn on, the chat activity card shows when the assistant is using a memory tool without revealing configuration content.

When Claude Code or Codex calls a tool from the `forge614-engram` MCP server, the card shows `🧠` and a readable name: for example, `🧠 memory search` instead of `mcp__forge614-engram__memory_search`. The brain identifies only the known Engram server; it does not guess that other servers are memory. Another MCP displays `server: tool`, for example `github: create_issue`.

Claude Code obtains the information from the SDK tool name: `mcp__<server>__<tool>`. Codex obtains it from `item.server` and `item.tool` in its `mcpToolCall` `app-server` notifications (the JSON-RPC protocol behind its interface). Those fields were verified with a real session before the indicator was implemented. Shared logic lives in `src/engines/mcp-labels.ts` and has dedicated tests.

## Three-scope memory and Engram notices

Like three shelves consulted at once — the person's, the hallway one shared with other repositories, and this project's — the chat hands the assistant the memory of the `shared`, `ecosystem` (the project's group, if it has one) and `project` scopes, in that order and inside the same data block, never as an instruction. With an Engram older than 1.6.0 there is no group scope and everything stays as before.

When Engram reports something, the chat shows it once in Shell's own text (es/en): that it updated its database so it can use groups (with the backup path), or that it re-linked the folder to the project declared in its `.forge614/project.json` file. If that file is invalid, Engram delivers no memory at all and Shell says so visibly; the chat keeps working without memory until the file is fixed or deleted.

The no-project reception screen (a list of recent projects, with each one's group) **does not exist yet**: decision 0003 declares it pending and it is not part of this delivery.

## Sessions and permissions

Codex lists and resumes threads in the current directory; it rejects a thread from another project or one active in another client. Each assistant keeps its native work modes, with the names and behavior it gives them, read from the assistant itself and never from a list written in Shell: Claude Code shows its SDK permission modes (Manual, Accept edits, Plan, Don't Ask, Auto, Bypass Permissions); Codex shows the choices of its own macOS permission menu, with its descriptions: «Ask for approval», «Approve for me» (only when Codex reports its `guardian_approval` feature on, as Codex's own menu decides; approvals then go to Codex's automatic reviewer) and «Full Access» (after Codex's «Enable full access?» confirmation, whose warning sits inside the question and goes away with it: it is not left written in the chat). They are narrowed by the restrictions Codex reports (`configRequirements/read`) and sent as the approval policy, reviewer and sandbox its protocol defines. Codex offers «Read Only» only on Windows, so Shell does not either; a remembered mode Codex no longer offers (such as Read Only) comes back as «Ask for approval» and Shell says so once. If an assistant rejects a mode, Shell says so in plain words and goes back to the previous one. Claude retains its native history. Before an action requiring confirmation, Shell shows the question in the interface, the same way for Claude Code and Codex (one shared formatter, `src/engines/permission-text.ts`). The request reads in plain words: first what the assistant wants to do in one sentence (its own description when it gives one — Bash's `description`, Codex's `reason` — otherwise a sentence built from the kind of action: «Run a command», «Edit 2 files», «Read a file», «Search the web», «Use the X tool of the Y MCP server»), then where (the folder, or the file paths with what each change does), then the command on its own, indented, exactly as written; none of the request's internal JSON is shown. Long descriptions, paths and field values are cut with «…» (a working folder longer than 48 characters keeps its last folders whole behind «…», so the card never breaks it in the middle of a name); the command is shown whole, and a request whose details are larger than 20000 characters is denied without being shown. Under the request there are only two rows with words, «Yes» and «No» (in Spanish «Sí» and «No»), with «Yes» first and marked so Enter alone approves; the down arrow (or the `N` key) chooses «No», the `Y` key chooses «Yes», and Esc is «No». A single footer says how to move and that `/f614:stop` cancels the turn. Typed `/f614:yes` and `/f614:no` still answer the pending question, but the screen no longer mentions them.

## Visible startup and welcome

Like waiting for an elevator while its arrow is moving, startup makes it clear that Shell is still working while it asks which engines are available.

In an interactive terminal, Shell displays the `Detecting installed AI engines…` spinner before opening the picker. Detection uses an asynchronous child process (`execFile`), rather than a synchronous wait that would freeze the process, so the animation can continue updating. On non-TTY output, it prints the same message once without animation. When the query finishes, the indicator is cleared and the normal flow continues.

The welcome frame renders `FORGE614` in bold and shows the Shell version as `v<version>` on the right when the terminal is wide enough. This identifies the application; it does not claim a Claude Code or Codex version.

## Transcript: activity, changes, and errors

Like a flight log, the history distinguishes routine events from moments that need inspection or a decision.

Routine tool calls—searches, reads, Bash, MCP/Engram, and similar events—render as a non-interactive bullet and, when available, one detail-preview line underneath. They have no border, background, or expand control: the summarized activity is all that is presented. Permission requests retain a full card because the person needs to read the context before deciding.

When Claude Code reports an `Edit` or `Write`, Shell shows a line-level diff instead of the tool's raw JSON: removed lines are red, added lines are green, context lines are muted, and a gutter shows line numbers. To keep the chat responsive, ordinary changes use a longest-common-subsequence comparison, oversized files fall back to a coarse view, and the display limits the diff to 60 rows before noting that more remain.

Claude Code and Codex both use an independent transcript view. Once you scroll away from the newest message, the floating `↓ New messages · jump to latest` button appears centered beneath the header; clicking it returns to the end. It hides automatically when the view is following the end again.

Errors such as a stopped turn, invalid command, invalid pending-permission response, or connection failure are inserted in red. `ChatText` accepts a base color so Markdown formatting preserves that visual signal instead of blending an error into an ordinary reply.

## Live status, model, and reasoning

Like the signal light on an operations console, the composer tells you whether writing can proceed, the engine is busy, or a human decision is needed.

`Ready` is green; `Working` is amber and replaces the static dot with a spinner; «Waiting for your answer» is red and shows for as long as Shell waits for you — a confirmation, a command's selector, a question or a permission request — even while the assistant is still working, and the box goes back to `Working` (or `Ready`) when you answer. During an active turn, Claude Code and Codex refresh the status every half second and show elapsed time, for example `Working · 12s`; during `/compact` in Codex the box says «Compacting context · …» instead. When a tool or command is running, the status also says what it is doing, for example `Working · Waiting for the PR #3 checks · 8m 23s` (the tool's description in Claude Code; the command, on a single line, in Codex); when none is running, only the time. Every time counter in Shell (this indicator, each tool and the sidebar) uses the same format: `45s`, `1m 27s`, `8m 23s`, `1h 02m`. A long command takes a single line in the chat that updates in place and freezes with its result when it ends. The counter stops when the turn finishes or is cancelled.

The `/model` and `/effort` menus are deliberate choices: they number options, align the primary column, and mark the active value with `✓` even while the cursor is on another option. This keeps the focused option distinct from the setting that will actually be used.

For Claude Code, the sidebar first tries to show the catalog's friendly name—for example, `Opus (1M context)`—rather than a technical identifier. If the selected value or telemetry has no exact catalog match, it turns the identifier into a readable fallback without inventing a product name.

Shell remembers selected model and reasoning independently for `claude` and `codex` in `~/.forge614/shell/preferences.json` (or under `FORGE614_HOME` when that is set). It also remembers the last assistant used (the startup picker marks it as «last used» and highlights it, so Enter accepts it) and, for each assistant, the last work mode, whichever it was (full access included), which it restores on opening without asking; a saved mode the assistant no longer has leaves its default mode, with no error. This is Shell-owned preference data; it does not modify the native CLI configuration. Reading and writing are best-effort conveniences: a missing or malformed file, a failed write, or a model no longer offered lets the session continue with available values.

In the sidebar, no explicit reasoning level is labeled `Default (auto)`. Claude Code's reasoning picker shows `Default (recommended)` and explains `Claude Code decides — shown in the sidebar after you send a message`: Claude does not report the concrete level it will resolve in advance, so Shell states that fact rather than guessing.

## Sidebar metrics

Like keeping consumption instruments beside the fuel gauge, the sidebar groups usage information together and leaves RAM as a process resource.

The latest message's tokens and the estimated amount sit under `PLAN USAGE`, before `RESOURCES`; they are no longer mixed with Shell or engine RAM. They are written in plain words over short rows, never cut off: `This message` / `read 2,996 tokens` / `wrote 700`, then `If you paid per use` / `≈ $0.67` / `your plan doesn't bill it`. The amount is a reference estimate, not a charge billed by Shell or by your plan; under one cent it reads `under $0.01` instead of zero.

Until the context has a figure, the `CONTEXT` section says when it will appear, in a short text that fits the sidebar's width: `after 1st message` in a new conversation, `after the next message` in a resumed one that has not been measured yet. Once there is a figure, the percentage in the circle is written as normal text with its «%» («8%»), on the circle's middle row and centered in it (a width of two or four cells, «8%» or «100%», can only sit half a cell to the left of the exact center); the percentage is also written beside it. The circle is always 13 cells wide and 7 rows tall, so a narrow sidebar is not broken.

The sidebar also takes over the left button's press, drag, and release, like the composer, so selecting text in the chat with the mouse no longer highlights the sidebar. Keeping the selection still while the screen scrolls is not solved yet.

Compact counts use `1M`, not `1000k`, and retain one decimal only when it adds information: `1.5k`, `43k`, `1M`, and `1.5M`. The context ring and filled portions of usage bars share an alert scale: normal below 85%, amber from 85%, and red from 100%. Color therefore conveys proximity to the limit, rather than merely a visual preference. The percentage in the middle of the context ring is normal text with its «%» («8%»); the ring is 13 cells wide and 7 rows tall.

## Background activity

When the active engine reports background work (Claude Code subagents, backgrounded processes), the sidebar shows a single line per activity, with its title, its state (running, done, failed) and elapsed time (when the title is long, the title is cut, not the state or the time); clicking it expands to show the result if the engine delivered it. The status bar adds a counter with an animated dot while activity is running (this is what remains there besides folder, branch, and Git state). If the engine does not report this distinctly, the sidebar says so explicitly instead of silently showing an empty list — see `docs/superpowers/specs/2026-09-22-background-activity-indicator-design.md`.
