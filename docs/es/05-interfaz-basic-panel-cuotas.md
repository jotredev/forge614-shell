# 05 — Interfaz Basic y chat

Como el tablero de un automóvil, la interfaz Basic muestra lo que el motor reporta; no inventa una aguja cuando el sensor no existe.

La interfaz Basic es la única interfaz visual disponible. El selector inicial pide confirmación incluso si hay una sola opción. Los asistentes de chat son Claude Code y Codex.

## Controles públicos dentro del chat

En Shell, un `/comando` sin prefijo es del asistente elegido (Claude Code o Codex) y hace lo que hace en la terminal normal de ese asistente. Todo comando propio de Shell empieza con `/f614:` y no queda ningún alias sin prefijo: `/f614:login` (Codex), `/f614:status` (Claude Code), `/f614:refresh`, `/f614:stop`, `/f614:quit`, `/f614:commands`, `/f614:help`, `/f614:yes` y `/f614:no`. Un nombre viejo sin prefijo que ya no existe responde «Comando desconocido: /x. Usa /f614:help.»; todo comando oficial de Codex tiene ruta, así que «Codex no permite /x desde Shell todavía» solo sale si la sesión no tiene el método de ese comando; con Claude Code, `/status` y `/help` los responde Shell con lo que tiene (ver sus filas; si el propio Claude Code lista uno, se le pasa a él), y cualquier otro nombre es «Comando desconocido». Los nombres salen de la lista de cada asistente: Codex 0.159.0 (`src/engines/codex/commands.ts`, copiada de su `slash_command.rs`) y Claude Code 2.1.274, la versión que trae el SDK instalado (su referencia de comandos, https://code.claude.com/docs/en/commands).

| Control | Efecto |
| --- | --- |
| `/login` (Claude Code), `/f614:login` (Codex) | Conecta Shell con la cuenta nativa existente u ofrece el flujo oficial. `/login` es un comando propio de Claude Code; Codex no tiene ninguno, así que con Codex es `/f614:login`, de Shell. |
| `/logout` | Desconecta solo esta sesión Shell; no revoca la cuenta. Antes de desconectar, Shell pregunta con una pregunta propia, no con la de permisos del asistente: «¿Desconectar Claude Code de esta Shell?» (con Codex, «¿Desconectar Codex de esta Shell?»), con el texto que explica que solo cambia esta sesión de Forge614-Shell (tu cuenta nativa, Orca, otras terminales y los chats guardados no cambian) y con qué comando reconectar, y dos opciones: «No, seguir conectado» (marcada) y «Sí, desconectar». Enter solo o Esc es «No» y no desconecta ni llama nada; solo «Sí, desconectar» desconecta. Nunca sale «Permiso solicitado» ni «¿Permitir?». |
| `/new` | Crea una conversación nueva del cliente. |
| `/resume` | Abre un selector con las conversaciones guardadas de este proyecto, la más reciente arriba. Cada fila muestra el título, la fecha, el primer mensaje y la carpeta, solo lo que el asistente informa. Las flechas se mueven, escribir filtra (título, primer mensaje y carpeta, sin distinguir mayúsculas ni acentos), Enter retoma la resaltada y Esc cancela sin cambiar nada. `/resume <número>` (la posición de la fila en esa lista) y, en Codex, `/resume <id>` siguen funcionando. Con Codex también funciona mientras Codex responde, como en Codex: la vista pasa a la conversación elegida y Shell deja de seguir el turno en curso. El título y el primer mensaje son los de la persona: el bloque de memoria que Shell manda al empezar (`<forge614-engram-memory>`) no cuenta. Al retomar (`/resume`) o bifurcar (`/fork`) cada mensaje viejo lleva la hora de su turno que informa Codex (`startedAt` para lo que escribiste, `completedAt` para la respuesta) y ninguna hora cuando Codex no la da; nunca la de ahora. |
| `/model`, `/effort` | Muestra o ajusta opciones que el cliente informa. `/effort` es de Claude Code; con Codex el esfuerzo de razonamiento se elige dentro de `/model`, como en Codex, y no existe `/effort` (ni `/thinking`, que ningún asistente tiene). Con Codex, `/model` también funciona mientras Codex responde, como en Codex; el modelo nuevo se aplica desde el siguiente turno y Shell lo avisa. |
| `/compact` | Codex: le pide al propio motor de Codex que compacte la conversación (`thread/compact/start`) y avisa cuando termina: en cuanto escribes `/compact`, la caja de estado dice «Compactando el contexto · Haciendo espacio para continuar · 12s», con el tiempo subiendo, hasta que termina: entonces la caja vuelve a «Listo» y el chat dice «Conversación compactada.» (sin barra de avance, porque Codex no informa avance real; en una caja angosta se quita la parte del medio y se conservan el título y los segundos); la memoria de Engram se vuelve a enviar con tu siguiente mensaje, igual que al abrir un hilo. Claude Code: pasa el comando a Claude Code. Un `/comando` de la lista de Codex se responde con «Codex no permite /x desde Shell todavía» solo si la sesión no tiene el método para él, no con «Comando desconocido». |
| `Shift+Tab` | Funciona en cualquier momento, también a mitad de un turno o con un permiso pendiente, y hace lo que hace en cada asistente. Claude Code: recorre sus modos de trabajo y aplica el cambio al instante. Codex: cambia su modo de colaboración, Default ↔ Plan, en el orden en que Codex los lista (`collaborationMode/list`), y nunca toca los permisos (esos se cambian con `/permissions`); a mitad de un turno Shell acepta el cambio y avisa en una línea que se aplicará en el siguiente turno. El indicador bajo la caja de mensaje sigue mostrando el permiso, agrega el «Plan mode» de Codex mientras Plan está activo y su ayuda dice «Shift+Tab: Plan ↔ Default». Shell recuerda el modo de colaboración y lo restaura al abrir. |
| `/status` | Propio de cada asistente. Con Codex muestra el estado reportado por el cliente y agrega la carpeta, el modo de trabajo y la conversación, como el `/status` de Codex. Cada línea de límite dice cuándo se reinicia en tu hora local y en tu idioma («Límite de 5 horas: 14% usado · se reinicia el 3 oct, 5:22 p.m. (último reporte)»), nunca como fecha de máquina. Cada límite se llama por lo que dura su ventana, como en el `/status` de Codex: «Límite de 5 horas», «Límite semanal», «Límite diario», «Límite mensual», «Límite anual», «Límite de N h», «Límite de N días» o «Límite de N min» para cualquier otra duración (cada ventana se reconoce con un margen del 5 %, como en Codex); cuando Codex no informa la duración dice «Límite de uso» (el segundo, «Límite de uso adicional»), y un límite que no es el propio de Codex añade su nombre después de la ventana («Límite semanal · GPT-5.3-Codex-Spark»). Nunca dice el «primary» ni el «secondary» de Codex, y los medidores de la barra lateral usan los mismos nombres. Los tokens de la sesión y el último contexto se leen como en la barra lateral: los totales con el separador de miles de cada idioma y el contexto en forma corta («Tokens de la sesión: entrada 39 356 · en caché 30 208 · salida 244» y «Último contexto: 20.2k / 258.4k»), no números crudos. Con Claude Code, `/status` muestra lo que el panel Status de Claude Code muestra y Shell de verdad tiene (ver su fila más abajo). Termina con una línea que dice de dónde llega la memoria: «Memoria: la entrega el asistente al arrancar» o «Memoria: la pega Shell» (ver «Memoria propia de Shell» en la guía de Engram). |
| `/status` (Claude Code) | El panel Status de Claude Code, con cada línea solo si Shell tiene el dato y sin inventar nada: `Versión` y `Servidores MCP` (agrupados por estado, un grupo por renglón y en este orden: «Conectados: a, b, c», «Conectando: …», «Necesitan iniciar sesión: …», «Fallaron: …», y después «Desactivados: …» y «Otros: …» para un estado sin nombre propio; un grupo sin servidores no aparece, y un renglón largo continúa debajo de su primer nombre, sin cortar ningún nombre) salen del mensaje `init` del turno más reciente, y `Sesión` de la conversación abierta, así que tras `/resume` ya aparece; antes del primer mensaje `Versión` y `Servidores MCP` no aparecen (y `Sesión` tampoco, salvo que se haya retomado una conversación) y una línea dice que aparecen tras él, y `/new` los borra otra vez hasta el primer mensaje de la conversación nueva; `Carpeta`; `Correo`, `Organización` y `Plan` de la cuenta que reporta el SDK al cargar el catálogo; `Llave de API` (de dónde sale la llave: `ANTHROPIC_API_KEY`, `apiKeyHelper`, creada con `/login`, o ninguna en uso) y, cuando el proveedor no es el propio de Anthropic, `Proveedor`; `Modelo` y `Modo de permisos` como los muestra la caja; `Memoria` (de dónde llega la memoria de Engram, como en la guía de Engram); y `Fuentes de configuración` (usuario, proyecto y local: los archivos que Shell le pide cargar a Claude Code). Lo que el panel de Claude Code muestra y Shell no tiene, no se muestra: comprobaciones de conectividad, las líneas de IDE y de proxy, el nombre de la sesión y qué archivos `CLAUDE.md` se encontraron. Corre también mientras hay un turno en curso, pero solo cuando Claude Code no lista `/status` por su cuenta; si lo lista, el comando se le pasa a Claude Code y espera a que termine el turno. Cuando lo responde Shell, no le manda nada al modelo. |
| `/f614:status` | Propio de Shell, con Claude Code: la telemetría de la sesión (modelo, tokens, contexto, costo y cuotas como los informa Claude Code). Cada límite se lee como en la barra lateral, con su nombre normal, su estado en palabras y su reinicio en hora local («Límite de 5 horas (último reporte): 31% usado | permitido | se reinicia el 3 oct, 5:22 p.m.»; los estados son «permitido», «permitido, cerca del límite» y «bloqueado», y un reinicio que no llegó dice «reinicio no reportado»); nunca muestra una clave del proveedor como `five_hour` ni una fecha de máquina. Antes era `/status` y `/forge614-status`. Codex no lo necesita: su propio `/status` ya lo muestra. Termina con una línea que dice de dónde llega la memoria: «Memoria: la entrega el asistente al arrancar» o «Memoria: la pega Shell». |
| `/f614:stop` | Propio de Shell, en Claude Code y en Codex: cancela la respuesta en curso. Antes era `/stop`, que ahora pertenece a Codex. En Codex pide interrumpir el turno (`turn/interrupt`) y espera la respuesta hasta 5 segundos; si Codex la confirma, espera hasta 5 segundos más a que Codex termine el turno; si Codex no responde a tiempo (Shell cierra entonces esa conexión, la abre de nuevo y retoma la misma conversación; solo si no puede reconectarse hay que reiniciar Shell), contesta con un error (por ejemplo, que no hay un turno en marcha) o no termina el turno a tiempo, Shell da el turno por terminado de su lado y lo avisa una sola vez, en tu idioma. |
| `/quit`, `/exit` | La «salida» propia de cada asistente (Claude Code: `/exit`, con `/quit` como alias; Codex: los dos): salen de Shell cuando no hay nada en curso y se niegan mientras haya un turno o un inicio de sesión, diciendo que `/f614:quit` sale (antes pregunta si detiene lo que corre). |
| `/f614:quit`, Ctrl+C, Ctrl+D | La salida propia de Shell, igual con Claude Code y con Codex, y aparece en el menú de `/` bajo FORGE614. Sin nada en curso sale de inmediato. Mientras corre un turno, un inicio de sesión o un comando pregunta «¿Salir de todos modos? Se detendrá lo que está en curso.» con «No» marcado: Enter y Esc lo conservan todo, y solo «Sí» (flecha y Enter, o la letra S) detiene lo que corre y sale. Con una pregunta de permiso abierta pide responderla primero. Reemplaza a `/quit!` y `/exit!`, que ya no existen. |
| `/f614:refresh` | Solicita de nuevo las cuotas que Codex o Claude informan; no envía un prompt de chat. Antes era `/refresh`. |
| `/f614:help`, `/f614:commands` | Propios de Shell: abren el menú de comandos para elegir. Antes eran `/help` y `/commands`; `/help` ahora es de Claude Code (ver la fila siguiente) y Codex no tiene `/help`. |
| `/help` (Claude Code) | La ayuda de Claude Code como Shell puede darla: la lista de comandos con su descripción — exactamente los que el menú de `/` muestra bajo CLAUDE CODE, primero los propios de Claude Code y luego los que Shell realiza con el significado de Claude Code (`/status` y `/help` entre ellos) —, una línea sobre los comandos propios de Shell con `/f614:`, y los atajos que Shell respeta: Enter (enviar), Shift+Enter (nueva línea), Shift+Tab (cambiar el modo de permisos), Tab (aceptar el comando marcado en el menú de `/`), Esc (cerrar un menú; en una pregunta de permiso responde «No») y Ctrl+C o Ctrl+D (salir de Shell, preguntando antes si hay trabajo en curso; con una pregunta de permiso abierta piden contestarla primero). Si la descripción de un comando o de un atajo no cabe en el ancho de la pantalla, lo que sigue baja debajo de su propia columna (sangría colgante); si el ancho es tan angosto que la columna no cabe, la descripción va en el renglón de abajo con una sangría fija de dos espacios. Los otros atajos de Claude Code (Ctrl+R, Ctrl+O, Ctrl+B, Option+P y demás) no se listan porque Shell no los tiene. Corre también mientras hay un turno en curso, pero solo cuando Claude Code no lista `/help` por su cuenta; si lo lista, el comando se le pasa a Claude Code y espera a que termine el turno. Cuando lo responde Shell, no le manda nada al modelo. |
| `/f614:yes`, `/f614:no` | Propios de Shell: responden un permiso pendiente escribiendo (lo normal es el selector con «Sí» marcado). Antes eran `/yes` y `/no`. |
| `$nombre` | Codex: el autocompletado de `$` lista el catálogo oficial de habilidades (skills: instrucciones reutilizables) de Codex desde `skills/list`, con las de plugins y sin las que Codex tiene apagadas. Cada `$nombre` reconocido en un mensaje se envía a Codex como una habilidad de verdad (`{ type: "skill", name, path }`) junto al texto del mensaje, que queda tal como lo escribiste; un `$palabra` que no es habilidad queda solo como texto. Al elegir una habilidad de la lista con Enter o Tab, Shell solo escribe `$nombre ` en la caja, como Codex, y sigues escribiendo: el siguiente Enter envía el mensaje. La lista se titula «HABILIDADES DE CODEX» y cuenta «Habilidades · 1–5 de 56» (en inglés «CODEX SKILLS» y «Skills · 1–5 of 56»); el menú de `/` sigue enviando el comando con Enter. |

Comandos propios de Codex, conectados por su app-server o, donde el propio Codex trabaja en local, en esta máquina (cada uno muestra un mensaje corto; los nombres de los comandos y de los modos de Codex, y las descripciones de su menú `/`, quedan como los tiene Codex; los mensajes propios de Shell van en el idioma de Shell, y los datos que llegan de Codex, como las descripciones y el detalle de los plugins, el motivo del revisor en `/approve` y los nombres de los modelos, quedan como los manda Codex):

| `/archive` | Archiva la conversación (`thread/archive`); tu siguiente mensaje empieza una nueva. |
| `/delete` | Antes pregunta «Sí / No» (Enter sobre «No», o Esc, no cambia nada) y luego borra la conversación para siempre (`thread/delete`). |
| `/goal`, `/goal <meta>`, `/goal clear` | Muestra, fija o borra la meta de una tarea larga (`thread/goal/get`, `set`, `clear`). |
| `/mcp`, `/mcp verbose` | Lista los servidores MCP configurados (conexiones con herramientas externas) y sus herramientas; verbose agrega versión, estado de inicio de sesión, dirección, número de recursos y la primera línea de la descripción de cada herramienta (`mcpServerStatus/list`). |
| `/hooks` | Muestra los hooks (acciones que Codex ejecuta solo en momentos fijos) con `hooks/list`; solo verlos, administrarlos no está conectado. |
| `/usage` | Muestra el uso de tokens de la cuenta (`account/usage/read`); usar un reinicio del límite de uso todavía no está conectado. |
| `/skills` | Lista las habilidades que Codex ofrece para esta carpeta (`skills/list`). |
| `/pwd` | Muestra la carpeta de trabajo; no llama a nada. |
| `/ps`, `/stop` | «Listar terminales en segundo plano» y «detener todas las terminales en segundo plano» de Codex (`thread/backgroundTerminals/list` y `/clean`). Esos dos métodos existen solo en el protocolo experimental de Codex, por eso Shell declara `experimentalApi` al conectarse. |
| `/permissions` | Abre el menú «Actualizar permisos del modelo» de Codex, con los nombres y descripciones de su menú de macOS (ver «Sesiones y permisos» abajo). |
| `/init` | Envía, como un mensaje normal, las instrucciones propias de Codex para escribir un archivo `AGENTS.md`, copiadas palabra por palabra de Codex (`src/engines/codex/prompts.ts`, con su dirección de origen). |
| `/diff` | Muestra los cambios de Git de la carpeta, incluidos los archivos sin seguimiento, como los calcula Codex; Shell corre Git por su cuenta, solo lectura, en la carpeta de la sesión. Fuera de un repositorio o sin cambios lo dice con las palabras de Codex. |
| `/apps` | Lista las apps y conectores que Codex informa (`app/list`), solo lectura, con búsqueda; Enter abre en el navegador la página de la app elegida, como en Codex. |
| `/experimental` | Lista las funciones beta de Codex (`experimentalFeature/list`). Shell no tiene casillas: Enter prende o apaga la elegida, la guarda con `config/batchWrite` y muestra su nuevo estado. |
| `/memories` | Los ajustes de memorias de Codex: «Usar memorias», «Generar memorias» (se guardan con `config/batchWrite`; la conversación abierta se actualiza con `thread/memoryMode/set`) y «Borrar todas las memorias» (`memory/reset`), que borra para siempre, por eso pregunta antes con «Volver» primero. Si las memorias están apagadas, pregunta «¿Activar las memorias?» con «Sí, activar» primero. |
| `/review`, `/review <texto>` | Corre la revisión de código de Codex (`review/start`). Sin texto ofrece las cuatro opciones de Codex: contra una rama base, cambios sin confirmar, un commit (ramas y commits salen del repositorio local, con búsqueda) o instrucciones propias; con texto, el texto son las instrucciones. Como en Codex, sale la línea «>> Revisión de código iniciada: … <<» (con lo que se revisa) y, al terminar, la línea «<< Revisión de código terminada >>» seguida del resultado, una sola vez. La revisión termina con el fin del turno que Codex devolvió al empezarla (`review/start`), aunque su sub-agente avise de otro turno; entonces la caja vuelve a «Listo». |
| `/fork`, `/fork <nombre>` | Copia la conversación (`thread/fork`), le pone nombre a la copia si se da uno (`thread/name/set`) y sigue en ella. No se hace la pregunta de Codex sobre un «worktree» nuevo: la copia queda en esta carpeta. |
| `/plan`, `/plan <texto>` | Cambia a Plan; con texto además envía el texto en Plan. Cuando un turno en Plan termina con un plan, Shell hace la pregunta «¿Implementar este plan?» de Codex con sus tres opciones: implementarlo en Default, empezar una conversación nueva con el plan o quedarse en Plan. |
| `/export` | Ofrece «Copiar al portapapeles» o «Guardar en un archivo»: toda la conversación en el Markdown de Codex (`thread/read`), guardada como `codex-session-<id>.md` en la carpeta sin sobrescribir nunca un archivo. `/export <ruta>` la guarda en esa ruta. |
| `/copy` | Copia al portapapeles la última respuesta, o uno de sus bloques de código o citas (en macOS con el `pbcopy` del propio sistema; no se instala nada). |
| `/mention` | Pone `@` en la caja de mensaje; lo que escribas después busca archivos de la carpeta con la búsqueda propia de Codex (`fuzzyFileSearch`), y la ruta elegida entra al mensaje como texto normal, como la manda Codex. |
| `/approve` | Lista las acciones que la revisión automática de Codex denegó hace poco en esta conversación (hasta diez, la más reciente primero, con el motivo del revisor) y aprueba un reintento de la elegida (`thread/approveGuardianDeniedAction`, con el evento de la denegación armado como lo arma Codex). Sin ninguna lo dice en una línea. El reintento sigue pasando por la revisión automática. Una solicitud de permisos denegada que pide acceso a archivos no se ofrece: su evento tiene otra forma y Shell no la adivina. |
| `/feedback` | El flujo de Codex: la categoría (error, mal resultado, buen resultado, revisión de seguridad, otro), si se envían los registros y una nota opcional, que se escribe en una caja de texto debajo de la pregunta. Como manda datos a OpenAI, después pregunta «¿Enviar esto a OpenAI?» con un resumen de lo que sale (tipo, nota, registros, conversación) y «No» marcado: Enter solo, Esc o «No» no envían nada y no se llama a `feedback/upload`; solo «Sí» lo envía. Después viene el seguimiento: con error, mal resultado, revisión de seguridad y otro muestra la dirección para abrir un reporte y el ID de la conversación; con buen resultado dice «¡Gracias por tu comentario!» y el ID, sin dirección; sin registros empieza con «Comentario guardado (sin registros).». El archivo de la conversación solo se adjunta si aceptas enviar los registros. |
| `/import` | Busca configuración para importar de Claude Code y de Cursor (`externalAgentConfig/detect`) y lista lo que encontró. Si Claude Code y Cursor tienen algo, primero pregunta «¿Desde dónde quieres importar?». Cada fila muestra [x] o [ ]: Enter marca o desmarca un elemento (todos empiezan marcados) y «Importar lo marcado» va primero. Como copiar escribe en `~/.codex`, pregunta «¿Copiar esto a ~/.codex?» diciendo exactamente qué se copia y desde dónde, y avisando en palabras normales que puede incluir la configuración de tus conexiones MCP (con sus llaves de acceso) y tus chats de Claude Code, con «No» marcado: Enter solo, Esc o «No» no copian nada, y solo «Sí» llama a `externalAgentConfig/import`. Cuando Codex avisa que la importación terminó (`externalAgentConfig/import/completed`), Shell redacta el aviso con su propio texto: cuántos se importaron y cuántos fallaron, por tipo. |
| `/plugins` | Lista los plugins de los marketplaces disponibles (`plugin/list`, los instalados primero, con búsqueda) y abre el detalle del elegido (`plugin/read`). La cuenta al pie de la lista («1–5 de 5015») cuenta solo plugins, así que dice lo mismo que la línea sobre la lista («Instalados 11 de 5015 plugins disponibles»): la fila «Marketplaces» no es un plugin. «Instalar plugin» y «Desinstalar plugin» preguntan antes («¿Instalar X?» / «¿Desinstalar X?», con «No» marcado) porque instalar descarga código de terceros: solo «Sí» llama a `plugin/install` o `plugin/uninstall`. Agregar, quitar y actualizar marketplaces no está conectado: su fila lo dice y no llama a nada; tampoco el paso guiado de conectar las apps de un plugin después de instalarlo, y Shell solo nombra las apps que aún lo necesitan. |
| `/recap` | El «resumir la conversación actual ahora» de Codex. Mientras trabaja, la caja dice «Generando el resumen de la conversación · 3s». Shell arma el prompt de resumen de Codex con los últimos ocho intercambios que ves en pantalla (nunca la salida de herramientas; como máximo 8.192 tokens estimados, los más viejos se descartan o se recortan por el medio) y le pide a Codex que lo escriba en una conversación temporal de solo lectura, sin herramientas, sin entorno y sin servidores MCP, que nunca se guarda: `config/read`, luego `thread/start` (efímero), `turn/start` con el esquema de la respuesta y siempre `thread/unsubscribe` al final, también si falla o si un paso se queda sin tiempo. Cada uno de los tres pasos tiene sus propios 30 segundos (arrancar el hilo, que es `config/read` y `thread/start`; el turno; y `thread/unsubscribe`), no 30 segundos en total. El resultado aparece como «↳ Resumen: …» y, si la hay, «Siguiente: …». Nada de lo que diga la conversación temporal llega al chat, y nunca aparece en `/resume`. Sin nada que resumir dice «No hay historial de la conversación para resumir.»; si no se puede hacer, «No se pudo generar el resumen. Inténtalo de nuevo.». No espera a que termine el turno: mientras corre un turno u otro comando no hace nada y responde «Espera al motor, o termina con /f614:stop la operación activa primero.» |
| `/side`, `/side <pregunta>`, `/btw` | Una conversación lateral: una rama temporal de la conversación actual para preguntar algo aparte (`/side` y `/btw` son el mismo comando en la lista de Codex). Shell lee las instrucciones de desarrollador de la configuración de Codex para la carpeta (`config/read`, `developer_instructions`), bifurca el hilo (`thread/fork`: efímero, sin copiar sus turnos con `excludeTurns`, con las instrucciones laterales de Codex añadidas después de las que ya tiene; si el servidor no conoce esa opción, Shell repite la bifurcación sin ella) e inyecta el ítem de límite de Codex (`thread/inject_items`); con `/side <pregunta>` la pregunta se envía enseguida (`turn/start` en el hilo lateral). Mientras dura, arriba de la vista dice «Conversación lateral (separada del hilo principal)»; en reposo la caja dice «Conversación lateral · del hilo principal · Ctrl+C para cerrar» (con «el principal necesita aprobación» antes de «Ctrl+C para cerrar» cuando el hilo principal espera una aprobación), y mientras la conversación lateral responde dice «Trabajando · Conversación lateral · 12s»: lo que escribes va al hilo lateral, nunca al principal, y lo que diga la conversación principal mientras tanto (sus respuestas, sus preguntas de permiso) espera y aparece cuando vuelves. Solo funcionan los comandos que Codex deja dentro de una conversación lateral (`/copy`, `/export`, `/diff`, `/mention`, `/status`, `/pwd`, `/usage`, `/agents`); cualquier otro responde «'/x' no está disponible en las conversaciones laterales. Pulsa Ctrl+C para volver primero al hilo principal.» **Para salir, pulsa Ctrl+C**: si la conversación lateral está respondiendo se interrumpe (`turn/interrupt`), se desconecta (`thread/unsubscribe`) y la conversación principal vuelve exactamente como estaba. La conversación lateral nunca se guarda. También se abre mientras Codex responde en el hilo principal; entonces Ctrl+D o `/f614:quit` siguen preguntando antes de detener ese trabajo. |
| `/subagents` | El selector «Subagentes» de Codex: primero la conversación principal («Principal [predeterminado]») y luego los subagentes que salieron de ella a cualquier profundidad, en el orden en que se crearon, cada uno con su nombre (ruta del agente, si no «apodo [rol]», si no solo el apodo, si no solo «[rol]»; sin nada de eso, su primer mensaje cortado a 80 caracteres, y sin nada en absoluto «Agente»), su estado (en ejecución, inactivo o cerrado) y su id, con búsqueda. Shell los encuentra con `thread/loaded/list` y `thread/read` (los que están en memoria) y con `thread/list` con `sourceKinds: ["subAgentThreadSpawn"]` y esta conversación como `ancestorThreadId` (los guardados, por páginas). Al elegir uno se muestra su conversación en solo lectura (`thread/read`) y se sigue mientras trabaja; en reposo la caja dice «Mirando a … · solo lectura · Ctrl+C para volver» y mientras el subagente trabaja dice «Trabajando · Mirando a … · 12s». Shell no puede enviarle mensajes a un subagente: escribir ahí lo dice y no envía nada. Ctrl+C, o elegir «Principal» otra vez en `/subagents`, vuelve a la conversación principal sin detener al subagente. Dentro funcionan los mismos comandos que en una conversación lateral, más `/subagents`. Sin subagentes dice «Todavía no hay agentes disponibles.». Si la función de subagentes de Codex está desactivada y no hay ninguno, pregunta «¿Activar los subagentes?» con «Sí, activar» marcado (como lo marca Codex) y dice en la propia pregunta que «Sí» escribe `features.multi_agent = true` en tu configuración de Codex (`~/.codex/config.toml`, con `config/batchWrite`) para las conversaciones nuevas; «Ahora no» y Esc no escriben nada. |
| `/agents` | Con el servidor embebido, que es el caso de Shell, Codex muestra «Agentes compartidos no disponibles»; Shell dice lo mismo («Esta sesión no está conectada a un servidor compartido en segundo plano.») y añade que Shell no inicia ese servidor. Codex ofrecería iniciar uno y explicaría que iniciarlo no movería la sesión; Shell no ofrece nada que iniciar y deja fuera esa explicación, porque solo confundía. Funciona dentro de una conversación lateral. |

Con Codex, el menú de `/` (y `/f614:commands`) lista los comandos de Codex con la descripción de Codex, en el orden de Codex, y solo los que Codex muestra en macOS; los propios de Shell (`/f614:login`, `/f614:refresh`, `/f614:commands`, `/f614:stop`, `/f614:quit`) van aparte bajo FORGE614, el único grupo cuyos comandos llevan prefijo. Con Claude Code el grupo FORGE614 tiene `/f614:refresh`, `/f614:status`, `/f614:commands`, `/f614:stop` y `/f614:quit`, y los comandos propios de Claude Code van bajo CLAUDE CODE (`/status` y `/help` incluidos). Los comandos que Codex deja correr mientras trabaja (`/model`, `/resume`, `/permissions`, `/rename`, `/goal`, `/mcp`, `/hooks`, `/usage`, `/skills`, `/pwd`, `/ps`, `/stop`, `/status`, `/copy`, `/diff`, `/mention`, `/apps`, `/approve`, `/plugins`, `/feedback`, `/side`, `/btw`, `/subagents`, `/agents`) lo hacen; los demás (`/recap` entre ellos) no esperan: mientras corre un turno u otro comando no hacen nada y responden «Espera al motor, o termina con /f614:stop la operación activa primero.» Un comando que solo existe en la pantalla de Codex (como `/theme`, `/vim` o `/voice`) se responde con «/theme solo existe en la pantalla de Codex.»; cualquier otro comando de la lista de Codex está conectado, así que «Codex no permite /x desde Shell todavía» es solo lo que respondería una sesión que no tiene esa petición; un nombre que no es de Codex es «Comando desconocido».

El panel lateral muestra la sesión, el modelo, el razonamiento, el contexto y las cuotas, y la barra de estado bajo el chat muestra solo lo que el panel no repite: trabajo en segundo plano, carpeta, rama y estado de Git. Si la cuenta no está conectada, la barra conserva además el aviso «Desconectado» con el comando que reconecta (`/f614:login` con Codex, `/login` con Claude Code), para que llegue también a una terminal demasiado angosta para el panel. El historial muestra la conversación, con cada herramienta con sangría bajo el mensaje del asistente al que pertenece. “No reportado” significa exactamente que el cliente no entregó el dato. La interfaz no soporta pantallas ni comandos de Gemini o Antigravity.

## Actividad de memoria Engram

Como ver encenderse una luz del archivador, la tarjeta de actividad del chat muestra cuándo el asistente está usando una herramienta de memoria, sin revelar el contenido de la configuración.

Cuando Claude Code o Codex llama una herramienta del servidor MCP `forge614-engram`, la tarjeta muestra `🧠` y un nombre legible: por ejemplo, `🧠 memory search` en lugar de `mcp__forge614-engram__memory_search`. El cerebro identifica solo el servidor conocido Engram; no infiere que otros servidores sean memoria. Para otro MCP se muestra `servidor: herramienta`, por ejemplo `github: create_issue`.

Claude Code obtiene el dato del nombre de herramienta que entrega su SDK: `mcp__<servidor>__<herramienta>`. Codex lo obtiene de `item.server` e `item.tool` en sus notificaciones `mcpToolCall` de `app-server` (protocolo JSON-RPC para su interfaz). Esos campos se verificaron con una sesión real antes de implementar el indicador. La lógica compartida está en `src/engines/mcp-labels.ts` y tiene pruebas propias.

## Memoria de tres ámbitos y avisos de Engram

Como tres estantes que se consultan a la vez —el de la persona, el del pasillo compartido con otros repositorios y el de este proyecto—, el chat entrega al asistente la memoria de los ámbitos `shared`, `ecosystem` (el grupo del proyecto, si lo tiene) y `project`, en ese orden y dentro del mismo bloque de datos, nunca como instrucción. Si Engram es anterior a 1.6.0 no hay ámbito de grupo y todo sigue igual.

Cuando Engram avisa algo, el chat lo muestra una sola vez con texto propio (es/en): que actualizó su base de datos para poder usar grupos (con la ruta de la copia de seguridad), o que volvió a vincular la carpeta con el proyecto que declara su archivo `.forge614/project.json`. Si ese archivo es inválido, Engram no entrega ninguna memoria y Shell lo dice de forma visible; el chat sigue funcionando sin memoria hasta que se corrija o se borre el archivo.

La pantalla de recepción sin proyecto (lista de proyectos recientes, con el grupo de cada uno) **todavía no existe**: el acta 0003 la declara pendiente y no forma parte de esta entrega.

## Sesiones y permisos

Codex lista y retoma hilos del directorio actual; rechaza un hilo de otro proyecto o activo en otro cliente. Cada asistente conserva sus modos de trabajo nativos, con los nombres y el comportamiento que él les da, leídos del propio asistente y nunca de una lista escrita en Shell: Claude Code muestra los modos de permisos de su SDK (Manual, Accept edits, Plan, Don't Ask, Auto, Bypass Permissions); Codex muestra las opciones de su propio menú de permisos en macOS, con sus descripciones: «Ask for approval», «Approve for me» (solo cuando Codex informa encendida su función `guardian_approval`, como lo decide el propio menú de Codex; entonces las aprobaciones las revisa el revisor automático de Codex) y «Full Access» (después de la confirmación «¿Activar acceso total?», cuya advertencia va dentro de la pregunta y desaparece con ella: no queda escrita en el chat). Se acotan con las restricciones que Codex informa (`configRequirements/read`) y se envían como la política de aprobación, el revisor y el sandbox que define su protocolo. Codex ofrece «Read Only» solo en Windows, así que Shell tampoco; un modo recordado que Codex ya no ofrece (como Read Only) vuelve como «Ask for approval» y Shell lo avisa una vez. Si un asistente rechaza un modo, Shell lo dice en palabras normales y vuelve al anterior. Claude mantiene su propio historial nativo. Antes de una acción que requiera confirmación, Shell muestra la pregunta en la interfaz, igual para Claude Code y para Codex (un solo formateador común, `src/engines/permission-text.ts`). La petición se lee en palabras normales: primero qué quiere hacer el asistente en una frase (su propia descripción cuando la da —la `description` de Bash, el `reason` de Codex—; si no, una frase armada según el tipo de acción: «Ejecutar un comando», «Editar 2 archivos», «Leer un archivo», «Buscar en la web», «Usar la herramienta X del servidor Y de MCP»), luego dónde (la carpeta, o las rutas de los archivos con lo que hace cada cambio) y luego el comando aparte, con sangría y tal como está escrito; nada del JSON interno de la petición se muestra. Las descripciones, rutas y valores largos se recortan con «…» (una carpeta de trabajo de más de 48 caracteres conserva sus últimas carpetas enteras tras «…», para que la tarjeta nunca la parta a la mitad de un nombre); el comando se muestra entero, y una petición cuyos detalles pasen de 20000 caracteres se deniega sin mostrarse. Debajo de la petición hay solo dos filas con palabras, «Sí» y «No» (en inglés «Yes» y «No»), con «Sí» primero y marcado para que Enter solo apruebe; la flecha abajo (o la tecla `N`) elige «No», la tecla `S` elige «Sí» y Esc es «No». Un único pie dice cómo moverse y que `/f614:stop` cancela el turno. Los comandos escritos `/f614:yes` y `/f614:no` siguen respondiendo la pregunta pendiente, pero la pantalla ya no los menciona.

## Arranque visible y bienvenida

Como esperar el ascensor viendo que la flecha se mueve, el arranque deja claro que Shell sigue trabajando mientras consulta qué motores están disponibles.

En una terminal interactiva, Shell muestra el spinner `Detecting installed AI engines…` antes de abrir el selector. La detección usa un proceso asíncrono (`execFile`), no una espera síncrona que congele el proceso; por eso la animación puede seguir actualizándose. En una salida sin TTY se imprime el mismo mensaje una vez, sin animación. Cuando termina la consulta, el indicador se limpia y continúa el flujo normal.

La bienvenida destaca `FORGE614` en negritas y muestra la versión de Shell como `v<versión>` a la derecha cuando el ancho de la terminal alcanza. Es información de identidad de la aplicación, no una afirmación sobre la versión de Claude Code o Codex.

## Aspecto: bloques sin bordes, grises neutros y colores que se adaptan

Como una sala oscura donde cada mesa es un poco más clara que el piso, la pantalla no dibuja cajas de líneas: cada zona (barra lateral, cuadro de escribir, tarjetas, bloques de código, opción elegida) es un bloque de fondo un poco más claro que el fondo general, y la separación sale del contraste y del espacio. Lo secundario va en gris apagado y los estados se distinguen por el color y el icono de su texto. La pantalla es siempre oscura: mientras está en la pantalla alterna, Shell pone el fondo general y el color base del texto detrás de todo lo que escribe (`workspaceTerminal`), también en las pantallas de arranque, y los restablece al salir.

Todos los colores están en un solo archivo, `src/ui/basic/theme.ts`. Los grises no tienen tinte azul; el índice de 256 colores es el que usa una terminal sin color verdadero:

| Nombre | RGB | Índice de 256 colores | Dónde se usa |
|---|---|---|---|
| `background` | 10;10;11 | 232 | fondo general de la pantalla |
| `surface` | 24;24;27 | 234 | barra lateral, cuadro de escribir, tarjetas, bloques de código |
| `elevated` | 39;39;42 | 235 | la opción del cursor en los menús del cuadro de escribir, el botón «ir al final» |
| `foreground` | 228;228;231 | 254 | texto |
| `muted` | 161;161;170 | 248 | texto secundario |
| `faint` | 63;63;70 | 238 | huecos de las barras de uso y del anillo, la regla `---` del Markdown |
| `accent` | 70;222;224 | 80 | acento (la rayita «▎» del cursor, títulos del chat, títulos de sección de la barra lateral) |

El estado (`success`, `warning`, `danger`), el diff (`added`, `removed`, `addedBackground`, `removedBackground`) y los colores de modo (`purple`, `planning`, `magenta`) conservan su valor.

**Colores que se adaptan.** `theme.ts` pregunta, cada vez que pinta, a `getCapabilities().trueColor` de pi-tui, que lo decide según la terminal: una reconocida (kitty, Ghostty, WezTerm, Warp, iTerm2, Windows Terminal, Alacritty, VS Code, Zed, JetBrains, la consola de Windows) tiene color verdadero; dentro de tmux o screen, y en cualquier terminal no reconocida, solo si `COLORTERM` vale `truecolor` o `24bit`; `PI_TRUE_COLOR` (`1` o `0`) manda sobre todo lo demás. Con color verdadero emite `38;2` / `48;2` (RGB); sin él, usa el índice más cercano de la paleta de 256 colores (el cubo de 6×6×6 y la rampa de 24 grises) con `38;5` / `48;5`, también para el fondo general y el texto base de la pantalla alterna. No se le avisa nada a la persona. Hay una sola función de conversión (`nearestAnsi256`), con pruebas de valores exactos. Con 256 colores, el fondo rojo y el verde de las filas de un diff caen ambos en el gris 235 (el cubo no tiene verdes ni rojos tan oscuros); sus signos `+` / `-` y el color del texto siguen distinguiéndolas.

**Qué cambió de forma.**

- El cuadro de escribir es un bloque de fondo `surface` de lado a lado, con dos columnas de margen sobre el fondo general y seis filas: una en blanco, un relleno, el editor, un relleno, el renglón de estado y modo y un relleno final. El estado ya no tiene fila propia arriba del editor: vive a la izquierda del renglón del modo (ver «Estado vivo, modelo y razonamiento»). En los menús del cuadro de escribir (comandos con `/`, selectores), la opción del cursor va en una fila de fondo `elevated` con una rayita «▎» en el acento en lugar de «›»; las demás filas no tienen fondo.
- El encabezado conserva sus tres filas, sin la regla de abajo.
- La barra lateral es una columna de fondo `surface` de arriba abajo, sin «│» y con dos columnas de relleno a cada lado; las dos columnas entre el chat y ella quedan con el fondo general, y de ahí sale el contraste. Los títulos de sección (`// SESIÓN`…) van en el color de acento (cian) y en negrita, sin regla debajo. El clic en las filas de actividad en segundo plano sigue funcionando.
- El botón «ir al final» es una sola fila de fondo `elevated`, sin caja.
- La tarjeta completa de una herramienta (un diff o un permiso) es un bloque `surface` con una columna de relleno a cada lado y una fila de relleno arriba y abajo, metido dos columnas desde el borde del chat, sin «│».
- Los bloques de código del chat ya no tienen la línea «───»: el código va sobre `surface`, la fila de apertura conserva solo el lenguaje (si lo hay) en gris secundario y la de cierre queda vacía. El componente Markdown de pi-tui solo le entrega al tema el texto de esas dos filas, así que no se pueden rellenar de lado a lado ni con fondo; el fondo del bloque queda detrás de cada fila de código, hasta donde llega su texto.
- En el arranque, la regla debajo de «FORGE614 / SHELL» y la que separaba los grupos de las acciones en la pantalla de grupo son ahora una fila en blanco: la altura es la misma.
- Las barras de uso y el anillo conservan `█`, `░` y el braille, con el hueco en `faint`.

## Transcripción: actividad, cambios y errores

Como un registro de vuelo, el historial separa los eventos rutinarios de los momentos que exigen inspección o una decisión.

Las llamadas rutinarias de herramientas —búsquedas, lecturas, Bash, MCP/Engram y similares— se renderizan como una viñeta no interactiva y, si hay detalle, una sola línea de vista previa debajo. No tienen borde, fondo ni control para expandir: la actividad resumida es todo lo que se presenta. Las solicitudes de permiso mantienen una tarjeta completa (un bloque de fondo `surface`, sin bordes) porque la persona debe poder leer el contexto antes de decidir.

Cuando Claude Code informa una edición `Edit` o `Write`, Shell presenta un diff por línea en vez del objeto JSON de la herramienta: líneas eliminadas en rojo, agregadas en verde, líneas de contexto atenuadas y un canal de numeración. Para proteger la fluidez del chat, el cálculo usa una comparación de subsecuencias comunes para cambios habituales, cae a una vista gruesa para archivos demasiado grandes y muestra como máximo 60 filas antes de indicar que quedan más.

Claude Code y Codex mantienen una vista de transcripción independiente. Al alejarse del último mensaje aparece, centrado bajo el encabezado, el botón flotante `↓ Mensajes nuevos · ir al final` (una sola fila de fondo elevado, sin caja); al pulsarlo vuelve al final. El botón se oculta automáticamente al volver a seguir el final del chat.

Errores como un turno detenido, un comando inválido, una solicitud de permiso sin respuesta válida o un fallo de conexión se insertan con texto rojo. `ChatText` acepta un color base para que el formato Markdown del error conserve esa señal visual, en lugar de confundirse con una respuesta normal.

## Estado vivo, modelo y razonamiento

Como el semáforo de una consola de operaciones, el compositor comunica si se puede escribir, si el motor está ocupado o si espera una decisión humana.

El estado vive en el renglón del modo, a la izquierda del texto del modo y separado de él por « · » en gris tenue: «<estado> · <modo>», con los atajos a la derecha. Si no cabe, se quitan primero los atajos, luego la parte del medio del estado (nunca el tiempo) y al final se recorta el renglón. El estado se distingue solo por el color del texto y su icono, sin fondos propios, cajas ni líneas: «✓ Listo» usa verde; «Trabajando» (y «Compactando…» o el resumen) lleva el giro braille en ámbar, su primera parte con una franja de luz que la recorre y el resto («· leyendo hola.sh · 12 s») en gris; «Esperando tu respuesta» usa rojo con un «●» que late; los demás estados («Verificando cuenta», «Conecta con /login») llevan un «●» fijo en el color que ya tenían. «Esperando tu respuesta» sale mientras Shell espera lo que respondas — una confirmación, el selector de un comando, una pregunta o una petición de permiso —, incluso si el asistente sigue trabajando, y la caja vuelve a «Trabajando» (o a «Listo») cuando respondes.

Tres animaciones, todas calculadas mezclando los colores de la paleta (y por eso se adaptan a 256 colores): la franja de luz avanza 7,5 letras por segundo desde 3 letras antes del inicio de la palabra hasta 3 después del final y vuelve a empezar, y cada letra mezcla entre un ámbar apagado y uno brillante según su distancia a la franja; el «●» de «Esperando tu respuesta» va y viene entre el rojo y el rojo mezclado a medias con el gris de la superficie, una vuelta cada 1,6 s; y cuando el estado pasa de trabajando a «Listo», «✓ Listo» arranca mezclado 60 % hacia blanco y vuelve al verde en 0,6 s (un «Listo» que no viene de trabajar, como el de al abrir, no destella). Mientras haya algo animado (trabajando, esperando o el destello) la pantalla se repinta cada 100 ms; cuando no hay nada animado no queda ningún temporizador corriendo. Mientras hay un turno activo, Claude Code y Codex actualizan además el estado cada medio segundo y muestran el tiempo transcurrido, por ejemplo `Trabajando · 12s`; durante `/compact` en Codex la caja dice «Compactando el contexto · …» en lugar de eso. Si hay una herramienta o un comando en curso, el estado dice también qué hace, por ejemplo `Trabajando · Esperando los checks del PR #3 · 8m 23s` (la descripción de la herramienta en Claude Code; el comando, en una sola línea, en Codex); si no hay ninguno, solo el tiempo. Todo contador de tiempo de Shell (este indicador, cada herramienta y la barra lateral) usa el mismo formato: `45s`, `1m 27s`, `8m 23s`, `1h 02m`. Un comando largo ocupa un solo renglón en el chat que se actualiza en su lugar y queda fijo con su resultado al terminar. Al terminar o cancelarse el turno, el contador se detiene.

Los menús de `/model` y `/effort` son elecciones explícitas: numeran las opciones, alinean la columna principal y marcan con `✓` el valor activo aunque el cursor esté sobre otra opción. Esto evita confundir la opción enfocada con la configuración que se usará realmente.

Para Claude Code, el sidebar intenta mostrar el nombre amigable que ofrece el catálogo —por ejemplo, `Opus (1M context)`— en vez de un identificador técnico. Si la elección o la telemetría no tienen una coincidencia exacta en el catálogo, aplica una conversión legible del identificador sin inventar un nombre de producto.

Shell recuerda por separado el modelo y el nivel de razonamiento elegidos para `claude` y `codex` en `~/.forge614/shell/preferences.json` (o bajo `FORGE614_HOME` si se definió). También recuerda el último asistente usado (el selector de arranque lo marca como «último usado» y lo deja resaltado, así que Enter lo acepta) y, por asistente, el último modo de trabajo, sea cual sea (también el de acceso total), que restaura al abrir sin preguntar; un modo guardado que el asistente ya no tiene deja su modo por defecto, sin error. Es una preferencia propia de Shell, no modifica la configuración nativa de los CLIs. Leer o escribir ese archivo es una comodidad de mejor esfuerzo: un archivo ausente o inválido, una escritura fallida o un modelo ya no ofrecido dejan que la sesión continúe con los valores disponibles.

En el sidebar, la ausencia de razonamiento explícito se llama `Default (auto)`. En el selector de razonamiento de Claude Code aparece `Default (recommended)` y explica `Claude Code decides — shown in the sidebar after you send a message`: Claude no comunica de antemano el nivel concreto que resolverá, por lo que Shell lo declara en vez de adivinarlo.

## Métricas del sidebar

Como agrupar los instrumentos de consumo junto al medidor de combustible, el sidebar coloca los datos de uso donde se interpretan juntos. Desde 1.13.0 ya no tiene la sección `RECURSOS` (la RAM de Shell y la del motor): se quitó entera, con su texto en español e inglés.

Los tokens del último mensaje y el importe estimado quedan debajo de `USO DEL PLAN`. Se escriben en palabras normales y en renglones cortos, sin cortes: `Este mensaje` / `leyó 2 996 tokens` / `escribió 700`, y luego `Si pagaras por uso` / `≈ $0,67` / `tu plan no lo cobra`. El importe es una referencia estimada, no un cargo de Shell ni de tu plan; si es menos de un centavo dice `menos de $0,01` en vez de cero.

Mientras el contexto no tiene cifra, la sección `CONTEXTO` dice cuándo aparecerá, con un texto corto que cabe en el ancho del panel: `tras el 1.er mensaje` en una conversación nueva, `tras el próximo mensaje` en una reanudada que aún no se ha medido. Cuando ya hay cifra, el porcentaje del círculo se escribe como texto normal con su «%» («8%»), en la fila del medio del círculo y centrado en él (un ancho de dos o cuatro celdas, «8%» o «100%», solo puede quedar media celda a la izquierda del centro exacto); el porcentaje también está escrito al lado. El círculo mide siempre 13 celdas de ancho y 7 filas de alto, así que el panel angosto no se rompe.

El panel también toma para sí presionar, arrastrar y soltar el botón izquierdo, igual que el compositor, así que seleccionar texto del chat con el ratón ya no resalta el panel. Que la selección se quede quieta al desplazar la pantalla todavía no está resuelto.

Los conteos compactos usan `1M`, no `1000k`, y conservan una decimal solo cuando aporta información: `1.5k`, `43k`, `1M` y `1.5M`. El anillo de contexto y las porciones llenas de las barras de uso comparten una escala de alerta: color normal por debajo de 85 %, ámbar desde 85 % y rojo desde 100 %. Así el color expresa cercanía al límite, no solo una preferencia estética. El porcentaje en el centro del anillo de contexto es texto normal con su «%» («8%»); el anillo mide 13 celdas de ancho y 7 filas de alto.

## Actividad en segundo plano

Cuando el motor activo reporta trabajo en segundo plano (subagentes de Claude Code, procesos backgroundeados), el panel lateral muestra un solo renglón por actividad, con su título, su estado (corriendo, hecho, fallido) y el tiempo transcurrido (si el título es largo, se recorta él, no el estado ni el tiempo); un clic la expande para ver el resultado si el motor lo entregó. La barra de estado añade un contador con el punto animado mientras haya actividad corriendo (es lo que queda ahí además de carpeta, rama y estado de Git). Si el motor no reporta esto de forma distinguible, el panel lo dice explícitamente en vez de mostrar una lista vacía silenciosa — ver `docs/superpowers/specs/2026-09-22-background-activity-indicator-design.md`.
